Actors (current version): System Administrator, Data Protection Steward, Academic Advisor, Wellbeing Advisor, Student Welfare Officer, Student, Programme Head
External: Google (personal account sign-in), Email service, External Support Services
Items marked (pending review) are kept for now but will be re-checked when we go over the requirements again.

System Administrator

- Manage accounts and roles:

Creating accounts for students and staff (one by one or in bulk from an import file), getting every account linked to its owner's personal Google account, and deciding which role each staff account plays.

+ Create a single account (email, full name, username, faculty, roles)
+ Bulk import accounts from an Excel file (email, full name, username, faculty code, role); importing from a Google Sheet is future (see AdviseCare_Future_List.txt)
+ Send account-linking emails to newly created accounts
+ Track each account's link status (not linked / email sent / linked) and resend the linking email
+ Edit account details (email, full name, username, faculty); changing the email unlinks the Google account, so the linking email has to be sent again
+ Activate/Deactivate or Ban/Unban an account (not the admin's own account; deactivating or banning ends all of the account's sessions)
+ Adjust roles for each account (the last System Administrator role cannot be removed)
+ View the account dashboard, sorted/filtered by role, faculty, link status or account status

- Manage faculties, subjects and advisor specialisations:

Setting up which faculties and subjects exist, and which subjects each academic advisor is specialised in, so academic support requests can be matched to the right advisor.

+ Create/edit/archive a faculty
+ Create/edit/archive a subject under a faculty
+ Link an academic advisor to the subjects they specialise in (no link = general academic advisor)
+ View advisors per faculty and per subject

- Define academic terms and reference master data:

Setting up the basic calendar and the shared lookup lists the rest of the system uses, including the support categories students pick from when they ask for help.

+ Create a term (name, start date, end date)
+ View term data
+ Set a term's status (upcoming/current/past); only one term can be current, so setting a new current term moves the old one to past
+ Create/edit/archive support categories (name, description, academic or wellbeing, governing consent purpose)

- Import student indicator data:

Since the school has no data source or API to connect to, indicator data (attendance, grades, ...) comes in as files that the admin uploads. The import is all-or-nothing: if one row is invalid, nothing is imported.

+ Upload an Excel/CSV file or a Google Sheet of indicator values
+ Map file columns to indicators
+ Validate the whole file before saving (all-or-nothing); valid values go straight into the student indicator history
+ View the import result and the list of invalid rows when it fails
+ View import history (who imported what, when; kept in the admin's activity log)

- Configure data source connections and ingestion schedules (future, not in the current version, see AdviseCare_Future_List.txt):

Kept in the ERD for later, when a real data source exists.

+ Add a data source (database, API endpoint) for one indicator (one data source per type of data)
+ Set ingestion schedule (time of day, frequency, on-failure policy)
+ Pause/Disconnect a data source
+ View failed ingestion jobs and retry them

- Restore records from backup and verify integrity after restore (future, not in the current version, see AdviseCare_Future_List.txt):

+ Select a backup point to restore from
+ Run the restore and the integrity check
+ View restore history log

- Configure system settings (not officially registered in docs):

An admin control panel for values that are fixed in code for now. It is kept out of the official reports; until a settings table exists (see the NOTES of AdviseCare_ERD_Tables.txt), the current values below are the defaults.

+ Choose which activity types are written to the activity log (every type in AdviseCare_Activity_Types.txt on by default)
+ Choose the access log granularity: one row per data attribute read (current) or one row per profile/page view
+ Set the session lifetime (current: 1 month)
+ Set how long the account-linking link (current: 7 days) and the password-reset link (current: 1 hour) stay valid
+ Set the default notification channels for new accounts (current: email and in-app both on) and which events also send an email
+ Set the avatar upload limits (current: PNG/JPEG/WEBP/GIF, up to 2 MB)
+ Set the import limits (maximum rows and file size for account and indicator imports)
+ Set the longest consent duration a student can choose, and the default expiry offered on the consent page (current: none)
+ Set the longest emergency access window a Steward can approve (current: no limit)
+ Set the default and maximum page size of paged lists
+ Set the overdue grace period for external referrals (current: overdue right after followUpDueAt)

Data Protection Steward

- Define indicators and shareable data attributes:

Deciding which pieces of student data exist in the system and can be shared. Each indicator has exactly one matching data attribute, and only these attributes can be offered to students when they share data with a case.

+ Create an indicator together with its data attribute (name, description, data type)
+ Edit the description shown to students
+ Archive an indicator/attribute that is no longer used (one-way; it can no longer be attached, granted or requested, but existing values and consents are kept)
+ View the list of indicators and attributes

- Define consent purposes and the attributes each purpose covers:

Deciding the reasons the university may use student data (e.g. "Academic advising", "Wellbeing support", "Financial support") and exactly which data attributes each reason covers.

+ Create a new consent purpose (name, description); it starts inactive until its attributes are attached and it is activated
+ Attach/Remove specific data attributes to a purpose
+ Activate/Deactivate a purpose
+ Retire (not remove) a purpose that is no longer used - Retired purposes cannot be brought back
+ View list of purposes and their status

- Configure access policies binding role, purpose and consent state:

Writing the actual rule: "a Wellbeing Advisor may see Family Situation only if the purpose is Wellbeing Support AND the student's consent for it is currently Granted." All three conditions have to line up together.

+ Create a policy - linking a role to a purpose (starts as a draft; the student's consent must be granted)
+ Activate a draft policy
+ View all policies affecting a given role
+ Revoke an existing policy
+ Test a policy against a sample case

- Review the access log and export processing records on demand:

Being able to pull up "who looked at what, when, and why", for audits and because data-protection law requires it.

+ Search/filter access log by user, student, date, or purpose
+ View detail of a single access event
+ Export a processing record for a specific student
+ Export a full report for a date range
+ Flag a suspicious access entry for follow-up

- Approve or reject requests for out-of-scope emergency access (pending review):

+ View pending emergency access requests (Stewards share one pool; the first Steward to act decides)
+ View requester's justification
+ Approve a request with time-limited scope
+ Reject a request with a reason
+ View history of past emergency access decisions

- Execute verified erasure of withdrawn attribute payloads:

When a student withdraws consent, the Steward triggers the destruction of the encryption key for that attribute, so the student's values become unreadable while the record that "this data existed and was withdrawn" stays for audit.

+ View queue of attributes pending erasure
+ Verify withdrawal is confirmed before erasing
+ Execute cryptographic erasure (destroy key)
+ Confirm audit trail remains intact after erasure
+ View erasure completion log

Academic Advisor and Wellbeing Advisor (shared requirements)

The two advisor roles use the same case tools. The Academic Advisor handles study matters (subjects, FLM / FAP / LMS resources) and may be specialised in some subjects. The Wellbeing Advisor handles personal life matters (psychological issues, accommodation, family, everyday money advice, paperwork such as student certificates or military exemption); anything involving borrowing money or financial support goes to the Student Welfare Officer.

- View assigned cases:

Their homepage: the cases the Programme Head matched to them, plus cases they opened themselves.

+ View list of assigned cases sorted by priority/stage/date
+ Filter cases by stage, category or subject
+ See count of new/unread cases
+ Open a case's full detail (reason, category, subject, shared data)

- Reach out to students based on indicators:

Advisors can also start a case themselves when a student's indicators (merits, attendance, grades...) suggest the student needs help. There is no automatic case opening.

+ View indicators of the students assigned to them (only what consent allows: "if you consent, we serve", attributes not shared are left out of the list)
+ Open a case for a student with a reason
+ Mark the case reason visible to the assigned advisor only or the authorized case team
+ Get the student notified that the advisor wants to meet

- Open a student profile with source provenance and missing-data notices:

Every value shown says where it came from (which import) and if something is missing, the system says so. Values the student did not consent to share are shown as "exists, not shared", never the value.

+ View student's consolidated profile
+ See which source each data point came from
+ See a notice where data is missing
+ View consent status for each visible section
+ Request additional data access if needed

- Record case notes and agreed actions:

Advisor and student decide by themselves how and when to meet (online, offline, external messaging app). The advisor writes down what was discussed. Once finalized, a note can't be edited.

+ Add a case note
+ Mark the note visible to the assigned advisor only or the authorized case team
+ Record agreed actions in the note
+ Edit a note before it's finalized
+ Finalize a note
+ View history of past notes for a student

- Advance a case through its stages:

Every case moves through a defined pipeline (pending, assigned, contacted, referred, follow-up, closed), giving a visible status instead of notes scattered across emails.

+ Move a case to the next stage
+ Record reason/outcome at each stage transition
+ Reopen a closed case
+ View a case's full stage-by-stage timeline

- Refer a case to another staff member:

The happy case is one advisor per student, but when needed the advisor can refer the case to another advisor (same or other type), and the Wellbeing Advisor can refer money matters to the Student Welfare Officer.

+ Create a referral (receiver, reason, priority)
+ View referral status (pending/accepted/returned)
+ Accept or return a referral received from someone else
+ Request a change of the assigned advisor (goes to the Programme Head)

- Reconstruct any advisee record as it stood on a past date:

Like a "way back machine": only when the advisor clicks, the system rebuilds what the student's record looked like on a chosen date.

+ Select a student and a target date
+ View the record exactly as it existed then
+ Compare two points in time side by side
+ See which changes occurred between the two dates

- Request additional consent scope from a student with stated purpose:

If an advisor needs data the student has not shared, they send a specific named request instead of relying on a blanket permission.

+ Select the student, the purpose and the attribute needed
+ State the purpose for the request
+ Send the request to the student
+ View request status (pending/granted/denied)
+ Withdraw a pending request

Student Welfare Officer

The Welfare Officer handles money: borrowing money, financial support, banking documents. The relationship is close to lawyer-client: the officer works through the paperwork and options with the student.

- Receive and triage referrals raised by advisors:

+ View incoming referral queue
+ Open referral detail with the advisor's notes
+ Set priority level for a referral
+ Accept or return a referral to the advisor

- Record financial interventions, support grants and outcomes:

+ Log an intervention (type, date, notes)
+ Record a support grant issued (loan, aid, fee deferral...)
+ Record the outcome of an intervention
+ Edit an intervention before it's closed
+ View intervention history for a student

- Link a student to external support services and track follow-up:

Connecting a student to a service outside the university (e.g. a money-lending service, a bank, a counselling centre). At minimum this serves as a recorded reminder of where the student was sent.

+ Select an external service to refer the student to
+ Record referral details and expected follow-up date
+ Log follow-up outcome when it comes back
+ Flag a follow-up as overdue

- Escalate cases to the Programme Head:

When a case goes beyond what the officer is allowed to decide, it is escalated to the Programme Head.

+ Mark a case for escalation
+ State the reason for escalation
+ View status of an escalated case
+ View the Programme Head's response

- View anonymised welfare statistics (pending review):

+ Select a term/date range
+ View anonymised summary statistics by category
+ Export the statistics

Student

- Maintain student identity and programme details:

+ Store an optional unique student code, current programme and academic status separately from login/account status
+ Allow profile details to be completed after account creation
+ Match indicator imports by student code, email or username when available

- Request support (create a case):

The main entry point: the student asks for help, picks the kind of help, explains why, and chooses which of their data to share.

+ Create a new case
+ Choose support type (academic / wellbeing)
+ Choose a category (academic: subject + topic; wellbeing: mental health, accommodation, money, ...)
+ Write the reason
+ Choose which data attributes to share (only those allowed by the category's consent purpose; can be left empty)
+ Receive the matched advisor's contact information by email and in-app notification
+ View own cases, their stages and history

- View own profile, indicators and the sources behind them:

+ View own consolidated profile
+ View own indicators and their sources
+ See notice where data about them is missing
+ View own consent status per section

- Grant or withdraw consent per purpose at any time:

+ View all purposes currently requesting/using data
+ Grant consent to a purpose
+ Withdraw single attributes of a purpose while keeping the rest shared
+ Set or change an optional expiry date for a consent
+ Withdraw consent entirely for a purpose
+ Respond to an advisor's consent request (grant/deny)
+ View consent change history

- See who accessed which part of their record and when:

+ View own access log
+ Filter access log by role or date
+ View the stated purpose for each access
+ Flag an access entry as suspicious

- Export own record:

+ Export own record and access log as a JSON file

- Request correction of an incorrect fact with advisor review (pending review):

+ Select the field believed to be incorrect
+ Submit correction with supporting explanation
+ Track correction request status
+ Withdraw a pending correction request

Programme Head

Usually there is one Programme Head for the whole app: the manager responsible for matching and oversight. The system does not limit it to one, so more can be added later.

- Match cases to advisors:

For now matching is manual; an automated/AI matching mode is a future plan.

+ View the queue of unassigned cases (type, category, subject, priority)
+ View suitable advisors (by type, subject specialisation, faculty, current workload)
+ Assign a case to an advisor (familiar advisor-student pairs suggested first: quality-of-life add-on, optional)
+ Reassign a case directly if needed

- Approve advisor assignment changes:

+ View pending assignment change requests
+ View reason and proposed advisor
+ Approve or reject the change
+ View history of past assignment changes

- Receive and respond to escalations:

+ View escalated cases
+ Record a response/decision
+ Close the escalation

- List, report and export cases:

+ List cases/consultations in a time range (filter by advisor, type, category, stage)
+ Review advisor caseload volume and case closure times
+ Export the list/report (Excel/CSV/PDF)

- View anonymised cohort indicators (pending review):

+ View cohort-level indicator summary
+ Filter by term or faculty
+ Export cohort summary

All authenticated users

- Sign in with Google or password:

Every account belongs to a personal Google account. After the first Google sign-in, the system offers to set a password. The user can skip it and set one later in Settings.

+ Link the personal Google account through the link in the account-linking email
+ Sign in with Google (only for accounts already linked; a Google account not linked to any account is refused)
+ Set a password at the account-setup step after the first Google sign-in (can be skipped)
+ Sign in with email/username and password
+ Reset a forgotten password by email (only for linked accounts; the reset logs out every session)
+ Log out (a session also ends on its own 1 month after sign-in)

- Receive notifications:

+ Receive in-app and email notifications (case assigned, advisor contact info, referral, consent request, escalation)
+ Mark a notification as read
+ Click through a notification to the relevant item
+ Set notification preferences (email vs in-app)
+ Clear (delete) old notifications

- Switch interface language between Vietnamese and English:

+ Select language from a menu/toggle
+ Have the interface update immediately
+ Have the selection persist across sessions

- View own activity history and account settings:

+ View own recent activity log
+ Edit account settings (username, avatar upload, notification preferences)
+ Change password, or set a first password if none exists (the old password is asked only when one already exists; the other sessions are logged out)
+ View active sessions and log out of other sessions
