IDENTITY & ACCESS

1. ACCOUNTS
accountId (PK) - uuid - unique identifier for every login-capable person in the system, referenced by nearly every other table as the actor who did something
facultyId (FK) - uuid - home faculty, taken from the faculty column of the import sheet; scopes students and academic advisors
avatarUrl - string - profile picture shown in headers, notifications, and caseload lists
email - string - the personal Gmail address of the user, used as login identifier, matched when linking the Google account, and where account emails (linking link, advisor contact info) are sent
fullName - string - display name shown across advisor caseloads, case notes, and reports
googleId - string - id of the personal Google account linked to this account, used by "Sign in with Google"; null until linked
authProvider - string - which method the user last signed in with (google/password), so login flow and security checks branch correctly
passwordHash - string - hashed password (never plaintext); null until the user sets one, either at the account-setup step right after the first Google sign-in (skippable) or later in Settings; while it is null, change-password asks for no old password
resetToken - string - SHA-256 hash of the one-time token carried by the account-linking email (valid 7 days) and by "forgot password" emails (valid 1 hour, linked accounts only); the token itself only exists in the email link, so a leaked database exposes no live links
resetTokenExpiresAt - date - expiry so a leaked/old reset link can't be reused indefinitely
userName - string - the handle used to log in and referenced in audit/activity trails
createdAt - date - when the account was provisioned, needed for account-creation history and auditing
linkStatus - enum - Google account linking state (notLinked/emailSent/linked), shown and sortable on the admin account dashboard
preferredLanguage - enum - drives "Switch interface language between Vietnamese and English"
status - enum - full lifecycle state (active/deactivated/banned) used by "Ban/Unban an account"

17. STUDENTDATA (bitemporal advising ledger)
studentDataId (PK) - uuid - unique identifier for one recorded value of one data attribute for one student
attributeKeyId (FK) - uuid - the student's key for this data attribute that encrypted this value (ATTRIBUTEKEYS); null for a missing row, which has no value
dataAttributeId (FK) - uuid - which data attribute this value belongs to (e.g. GPA)
dataSourceId (FK) - uuid - the data source the value was ingested from (future scheduled ingestion); null for values imported from an Excel/CSV file or Google Sheet, which go straight into this table
studentId (FK) - uuid - which student the value belongs to
termId (FK) - uuid - which academic term this value is scoped to
dataValue - string - the recorded value, stored encrypted (VARBINARY: format version + nonce + tag + AES-256-GCM ciphertext) with the student's key for this attribute; tied to its key, student, attribute, row and field, so it cannot be moved to another row; null for a missing row and after an erasure
provenanceNote - string - human-readable statement of where this value came from (e.g. imported file name and import date) and any caveats, satisfying the "state source" requirement; the only source information for imported values, since their dataSourceId is null
erasedAt - date - when an erasure cleared this value (dataValue set to null in the same step as destroying the key); null while the value is readable
transactionFrom - date - bitemporal field (system time): when this row became known to the system (when the value was imported or the correction approved); a row stays the system's current belief until the next row for the same student/attribute/term, so its end is derived from the next row's transactionFrom (no transactionTo column, rows are never updated)
validFrom - date - bitemporal field (valid time): when this value became true in the real world; it stays true until the next row's validFrom (no validTo column)
isMissing - bool - flags that a value for this attribute and term is expected but absent for this student, satisfying the "missing-data notice" requirement; a missing row has no key and no value
status - enum - what kind of row this is when inserted (original/correction); never changed afterwards since rows are insert-only

- FUTURE, not in this ERD (would need new tables):
  + In-app meeting scheduling: advisor time slots, student booking, advisors swapping meetings
  + In-app chat between advisor and student (possible stretch goal)
  + Backups and erasure: a backup taken before an erasure still holds the old wrapped key, so restoring it must re-apply completed erasures (destroy those keys again)
  + Master key rotation: re-wrap every attribute key with a new master key (the v1 prefix of each value leaves room for a new format)
  + Account import that also updates existing accounts: a row whose studentCode already exists updates that student (e.g. academicStatus), a new studentCode creates the account like today; until then the admin edits a student's profile one by one
  + Programme of each student: only needed once there is more than one programme / Programme Head; the faculty on ACCOUNTS is used for now
  + Admin configuration panel (not officially registered in docs): a SYSTEMSETTINGS key/value table (settingKey, settingValue, updatedBy, updatedAt) holding the settings listed in AdviseCare_Functional_Requirements.txt; until then the values are fixed in code/appsettings.json
- Imports and ingestion jobs are all-or-nothing: one invalid row fails the whole import and nothing is written.
- STUDENTDATA has no transactionTo/validTo: each row's end time is the transactionFrom/validFrom of the next row for the same student, attribute and term.
- Point-in-time views use either time axis: system time ("what the system knew on date X": the latest row with transactionFrom up to X) or valid time ("what was true on date X by today's knowledge": among rows with validFrom up to X, the latest validFrom, a later transactionFrom winning on ties).
- Bitemporal / history data is create-read-delete only, never updated through the API: STUDENTDATA (except erasure clearing dataValue), CASESTAGEHISTORIES, CONSENTHISTORIES, ACCESSLOGS (except its review fields isFlagged/status), and CASENOTES once finalized.
- Point-in-time reconstruction ("way back machine") is computed only when an advisor asks for a past date; nothing is precomputed.
- Removed in this version: EVENTCATEGORIES, EVENTS, EVENT_REGISTRATION. Removed columns: CONSENTS.narrowedAt and the "narrowed" consent state (a student shares or withdraws per attribute instead), ACCESSPOLICIES.requiredConsentStatus (only "granted" was left) and ACCESSPOLICIES.isActive / DATASOURCES.isActive (the status enum of the same table already says it).
- INDICATORS was merged into DATAATTRIBUTES (they were one to one) and STUDENTINDICATORS renamed to STUDENTDATA. Archiving a data attribute is one-way: it can no longer be attached to a purpose, granted, requested or imported (import rows for it are rejected and listed, the other rows are still imported), but existing values and consents are kept and still apply.
- Removed in this version as well: ADVISORASSIGNMENTS (advisors are linked to students only through CASES.advisorId) and ASSIGNMENTCHANGEREQUESTS, replaced by CASECHANGEREQUESTS (a change of advisor is requested per case).
- Access guard ("if you consent, we serve"): staff may read a student's attribute only when the student has a granted, unexpired consent on it under a purpose that is active, still covers the attribute (PURPOSE_ATTRIBUTE) and has an active access policy for one of the staff member's roles. Inside a case only the case category's purpose counts; outside a case (e.g. a student's data read outside a case) any such purpose counts, and attributes not consented are simply left out. A consent is given to everyone holding a role that has a policy for the purpose, not to one named advisor, so the guard does not check which advisor is asking (by design). Every allowed read writes one ACCESSLOGS row per attribute; students reading their own data are not logged.
- Consent expiry is checked when data is read (no background job): a granted consent past expiresAt gives no access until the student renews it.
- Erasure: ATTRIBUTEKEYS holds one key per student per attribute, so withdrawing a consent queues an ERASUREREQUESTS row only when the attribute is no longer granted under any purpose and the student has an active key for it; the Steward executes it in one save: the key is destroyed (wrappedKey null, status = destroyed) and every STUDENTDATA value and CORRECTIONREQUESTS value under that key is cleared (erasedAt set). A backup taken before the erasure still holds the old wrapped key, so before restoring one the completed erasures must be re-applied (until the master key version it used is deleted).
- Emergency access: Stewards share one pool of requests; the first Steward to approve or reject is stored in stewardId (a rejection needs a rejectionReason). While approved and before scopeExpiresAt, the requester may read every attribute of that student through the access guard; each read is logged with consentPurposeId = null. The access ends on its own at scopeExpiresAt.
- Encryption (envelope encryption, AES-256-GCM): the master keys live only in server configuration (Encryption:MasterKeys, numbered versions, plus Encryption:CurrentVersion). Each student/attribute key in ATTRIBUTEKEYS is wrapped with a key derived (HKDF) from one master key version and that row's ids, and its masterKeyVersion is stored. Each value in STUDENTDATA/CORRECTIONREQUESTS is encrypted with that key and tied to key, student, attribute, row and field. Users never receive a key: the server decrypts in memory only after the access guard allows the read, and API responses are sent with Cache-Control: no-store. Withdrawing a consent stops access at the guard at once; erasure is the later step that makes the stored values unreadable to everyone. Rotation: a new master key version is added, the Steward rewraps every active key (values are not re-encrypted), and an old version is deleted from the configuration once no kept database backup still needs it, after which erased values are unrecoverable from those backups too. Losing every copy of a master key makes its values unreadable, so each version is kept by two team members offline and only in the hosting's environment variables.
- Student data comes in three kinds, each with its own access rule:
  + Directory data: email, fullName, userName, faculty (ACCOUNTS) and studentCode, academicStatus (STUDENTPROFILES). Supplied by the school through the account import; every staff role (including every advisor) may read it at any time, with no consent and no access log, since the app cannot route or handle a case without it.
  + Data attributes (values in STUDENTDATA, defined by DATAATTRIBUTES): everything else that describes or measures the student. Readable only through the access guard (consent), and every read is logged in ACCESSLOGS, even when consent was given.
  + Case records (CASES, CASENOTES, CASESTAGEHISTORIES, REFERRALS, INTERVENTIONS, SUPPORTGRANTS, EXTERNALREFERRALS, ESCALATIONS): visible to the people working on the case; not consent-based and not written to ACCESSLOGS.
- STUDENTPROFILES exists only for Student accounts; it is created in the same save as the account (account import, single create, or giving the Student role) and only the admin edits it. The account import sheet always has 5 filled columns for staff rows (email, fullName, userName, facultyCode, role) and 7 for Student rows (+ studentCode, academicStatus), never anything in between.
- Usually one Programme Head for the whole app (the manager), but the system allows more. PROGRAMMES is kept but not used by other tables for now.
