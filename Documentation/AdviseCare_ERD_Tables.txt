IDENTITY & ACCESS

1. ACCOUNTS
accountId (PK) - uuid - unique identifier for every login-capable person in the system, referenced by nearly every other table as the actor who did something
facultyId (FK) - uuid - home faculty, taken from the faculty column of the import sheet; scopes students and academic advisors
avatarUrl - string - profile picture shown in headers, notifications, and caseload lists
email - string - the personal Gmail address of the user, used as login identifier, matched when linking the Google account, and where account emails (linking link, advisor contact info) are sent
fullName - string - display name shown across advisor caseloads, case notes, and reports
googleId - string - id of the personal Google account linked to this account, used by "Sign in with Google"; null until linked
authProvider - string - which method the user last signed in with (google/password), so login flow and security checks branch correctly
passwordHash - string - hashed password (never plaintext); null until the user sets one, either at the account-setup step right after the first Google sign-in (skippable) or later in Settings; while it is null, change-password asks for no old password
resetToken - string - SHA-256 hash of the one-time token carried by the account-linking email (valid 7 days) and by "forgot password" emails (valid 1 hour, linked accounts only); the token itself only exists in the email link, so a leaked database exposes no live links
resetTokenExpiresAt - date - expiry so a leaked/old reset link can't be reused indefinitely
userName - string - the handle used to log in and referenced in audit/activity trails
createdAt - date - when the account was provisioned, needed for account-creation history and auditing
linkStatus - enum - Google account linking state (notLinked/emailSent/linked), shown and sortable on the admin account dashboard
preferredLanguage - enum - drives "Switch interface language between Vietnamese and English"
status - enum - full lifecycle state (active/deactivated/banned) used by "Ban/Unban an account"

15. INGESTIONSCHEDULES
ingestionScheduleId (PK) - uuid - unique identifier for one ingestion schedule
dataSourceId (FK) - uuid - which source this schedule pulled from
scheduledStartTime - timeOnly - the time of the day this schedule is set, used to set the expected start time of each job of this schedule

lastRun - date - the recorded completedAt time of the last run job
numberOfSuccesses - int - total count of succeeded jobs
numberOfFails - int - total count of failed jobs

failureRetryInterval - int - the time in between retries (in seconds), only exist if onFailure is 'retry', otherwise null
numberOfRetries - int - as the name can tell, number of retries, only exist if onFailure is 'retry', otherwise null
status - enum - status of the schedule (active/paused/archived)

16. INGESTIONJOBS
ingestionJobId (PK) - uuid - unique identifier for one run of an ingestion job

17. STUDENTINDICATORS (bitemporal advising ledger)
studentIndicatorId (PK) - uuid - unique identifier for one recorded indicator value for one student
dataSourceId (FK) - uuid - the data source the value was ingested from (future scheduled ingestion); null for values imported from an Excel/CSV file or Google Sheet, which go straight into this table
indicatorId (FK) - uuid - which kind of indicator this value represents
studentId (FK) - uuid - which student the value belongs to
termId (FK) - uuid - which academic term this value is scoped to
indicatorValue - string - the actual recorded value (kept as string to accommodate numeric/categorical/boolean types uniformly)
provenanceNote - string - human-readable statement of where this value came from (e.g. imported file name and import date) and any caveats, satisfying the "state source" requirement; the only source information for imported values, since their dataSourceId is null
transactionFrom - date - bitemporal field: when this row became known to the system (system time, i.e. when the value was imported); a row stays the system's current belief until the next row for the same student/indicator, so its end is derived from the next row's transactionFrom (no transactionTo column, rows are never updated)
validFrom - date - bitemporal field: when this value became true in the real world (valid time); it stays true until the next row's validFrom (no validTo column)
isMissing - bool - flags that this indicator is expected but absent for this student, satisfying the "missing-data notice" requirement
status - enum - what kind of row this is when inserted (e.g. original/correction); never changed afterwards since rows are insert-only, and whether the value has been erased is read from the student's ATTRIBUTEKEYS row for that attribute

NOTES (current version)

- Current version: indicator data enters only through manual Excel/CSV/Google Sheet imports, which write straight into STUDENTINDICATORS with dataSourceId = null; the source of each imported value is kept in provenanceNote. DATASOURCES - INDICATORS is one to one (one data source per type of data).
- FUTURE, already in this ERD (tables are designed, but no feature is built for them in the current version):
  + Scheduled data ingestion / live integration with FAP, FLM, LMS: DATASOURCES, INGESTIONSCHEDULES, INGESTIONJOBS (and STUDENTINDICATORS.dataSourceId)
  + Stored report history: REPORTS (in the current version, case reports and the student JSON export are generated and downloaded on the fly, not stored)
  + Backup and restore with integrity check: BACKUPS, RESTOREOPERATIONS
  + Automated / AI case matching: no extra table needed, it would use CASES, ADVISORASSIGNMENTS, ACCOUNT_SUBJECT and SUBJECTS (incl. prioritising a familiar advisor-student pair)
  + Advising effectiveness analysis: no extra table needed, it would use CASES, CASESTAGEHISTORIES, REFERRALS and INTERVENTIONS
- FUTURE, not in this ERD (would need new tables):
  + In-app meeting scheduling: advisor time slots, student booking, advisors swapping meetings
  + In-app chat between advisor and student (possible stretch goal)
  + Admin configuration panel (not officially registered in docs): a SYSTEMSETTINGS key/value table (settingKey, settingValue, updatedBy, updatedAt) holding the settings listed in AdviseCare_Functional_Requirements.txt; until then the values are fixed in code/appsettings.json
- Imports and ingestion jobs are all-or-nothing: one invalid row fails the whole import and nothing is written.
- STUDENTINDICATORS has no transactionTo/validTo: each row's end time is the transactionFrom/validFrom of the next row for the same student and indicator.
- Bitemporal / history data is create-read-delete only, never updated through the API: STUDENTINDICATORS, CASESTAGEHISTORIES, CONSENTHISTORIES, ACCESSLOGS (except its review fields isFlagged/status), and CASENOTES once finalized.
- Point-in-time reconstruction ("way back machine") is computed only when an advisor asks for a past date; nothing is precomputed.
- Removed in this version: EVENTCATEGORIES, EVENTS, EVENT_REGISTRATION. Removed columns: CONSENTS.narrowedAt and the "narrowed" consent state (a student shares or withdraws per attribute instead), ACCESSPOLICIES.requiredConsentStatus (only "granted" was left) and ACCESSPOLICIES.isActive / DATASOURCES.isActive (the status enum of the same table already says it).
- Archiving INDICATORS / DATAATTRIBUTES is one-way and done as a pair: an archived attribute can no longer be attached to a purpose, granted or requested, but existing values and consents are kept and still apply.
- Access guard ("if you consent, we serve"): staff may read a student's attribute only when the student has a granted, unexpired consent on it under a purpose that is active, still covers the attribute (PURPOSE_ATTRIBUTE) and has an active access policy for one of the staff member's roles. Inside a case only the case category's purpose counts; outside a case (e.g. an advisor's student list with indicators) any such purpose counts, and attributes not consented are simply left out. Every allowed read writes one ACCESSLOGS row per attribute; students reading their own data are not logged.
- Consent expiry is checked when data is read (no background job): a granted consent past expiresAt gives no access until the student renews it.
- Erasure: ATTRIBUTEKEYS holds one key per student per attribute, so withdrawing a consent queues an ERASUREREQUESTS row only when the attribute is no longer granted under any purpose and the student has an active key for it; the Steward executes it by destroying the key (wrappedKey wiped, status = destroyed).
- Emergency access: Stewards share one pool of requests; the first Steward to approve or reject is stored in stewardId. An approved access ends on its own at scopeExpiresAt.
- Usually one Programme Head for the whole app (the manager), but the system allows more. PROGRAMMES is kept but not used by other tables for now.
