1. ACCOUNTS
accountId (PK) - uuid - unique identifier for every login-capable person in the system, referenced by nearly every other table as the actor who did something
facultyId (FK) - uuid - home faculty, taken from the faculty column of the import sheet; scopes students and academic advisors
avatarUrl - string - profile picture shown in headers, notifications, and caseload lists
email - string - the personal Gmail address of the user, used as login identifier, matched when linking the Google account, and where account emails (linking link, advisor contact info) are sent
fullName - string - display name shown across advisor caseloads, case notes, and reports
googleId - string - id of the personal Google account linked to this account, used by "Sign in with Google"; null until linked
authProvider - string - which method the user last signed in with (google/password), so login flow and security checks branch correctly
passwordHash - string - hashed password (never plaintext); null until the user sets one, either at the account-setup step right after the first Google sign-in (skippable) or later in Settings; while it is null, change-password asks for no old password
resetToken - string - SHA-256 hash of the one-time token carried by the account-linking email (valid 7 days) and by "forgot password" emails (valid 1 hour, linked accounts only); the token itself only exists in the email link, so a leaked database exposes no live links
resetTokenExpiresAt - date - expiry so a leaked/old reset link can't be reused indefinitely
userName - string - the handle used to log in and referenced in audit/activity trails
createdAt - date - when the account was provisioned, needed for account-creation history and auditing
linkStatus - enum - Google account linking state (notLinked/emailSent/linked), shown and sortable on the admin account dashboard
preferredLanguage - enum - drives "Switch interface language between Vietnamese and English"
status - enum - full lifecycle state (active/deactivated/banned) used by "Ban/Unban an account"

17. STUDENTDATA (bitemporal advising ledger)
studentDataId (PK) - uuid - unique identifier for one recorded value of one data attribute for one student
attributeKeyId (FK) - uuid - the student's key for this data attribute that encrypted this value (ATTRIBUTEKEYS); null for a missing row, which has no value
dataAttributeId (FK) - uuid - which data attribute this value belongs to (e.g. GPA)
dataSourceId (FK) - uuid - the data source the value was ingested from (scheduled ingestion, extra scope ES1); null for values imported from an Excel/CSV file or a transcript PDF, which go straight into this table
studentId (FK) - uuid - which student the value belongs to
subjectId (FK) - uuid - the subject of a value of a per-subject data attribute (DATAATTRIBUTES.isSubjectSpecific), e.g. Attendance rate in PRN212; null for a per-term data attribute; taken from the subject code column of the import
termId (FK) - uuid - which academic term this value is scoped to
dataValue - string - the recorded value, stored encrypted (VARBINARY: format version + nonce + tag + AES-256-GCM ciphertext) with the student's key for this attribute; tied to its key, student, attribute, row and field, so it cannot be moved to another row; null for a missing row and after an erasure
provenanceNote - string - human-readable statement of where this value came from (e.g. imported file name and import date) and any caveats, satisfying the "state source" requirement; the only source information for imported values, since their dataSourceId is null
erasedAt - date - when an erasure cleared this value (dataValue set to null in the same step as destroying the key); null while the value is readable
transactionFrom - date - bitemporal field (system time): when this row became known to the system (when the value was imported or the correction approved); a row stays the system's current belief until the next row for the same student/attribute/term/subject, so its end is derived from the next row's transactionFrom (no transactionTo column, rows are never updated)
validFrom - date - bitemporal field (valid time): when this value became true in the real world; it stays true until the next row's validFrom (no validTo column)
isMissing - bool - flags that a value for this attribute and term is expected but absent for this student, satisfying the "missing-data notice" requirement; a missing row has no key and no value; only per-term attributes get missing rows, because AdviseCare does not know which subjects a student takes
status - enum - what kind of row this is when inserted (original/correction); never changed afterwards since rows are insert-only

NOTES (current version)

- Relationship lines (changed 21/11/2026, Q-265): "A - B: x : y (fk)" where x is how many A rows go with one B row and y how many B rows go with one A row, as on the draw.io cardinality legend: 1 = exactly one (the FK is NOT NULL), 0..1 = zero or one (the FK allows null, or the FK is unique for a one to one), 0..N = zero or more, 1..N = one or more. 1..N is used only where the code always creates the child row with its parent: CASES - CASESTAGEHISTORIES (a case gets its first stage row when it is created), CONSENTS - CONSENTHISTORIES (a consent gets its first history row when it is granted) and ATTRIBUTEKEYS - STUDENTDATA (a key is created for the first value it encrypts). Many to many lines name the junction table: ACCOUNTS 0..N : 1..N ROLES (every account has at least one role; exactly one in the current version), the other three junctions are 0..N : 0..N. CASES - INDICATORFLAGS is 0..1 : 0..1: a flag opens at most one case and a case comes from at most one flag (both ends optional).
- Current version: student data enters only through manual imports, which write straight into STUDENTDATA with dataSourceId = null: Excel/CSV files (any data attribute; importing from a Google Sheet is extra scope, ES6) and transcript PDFs (a grade transcript fills the per-subject Subject mark, an attendance file the per-subject Attendance rate); the source of each imported value is kept in provenanceNote. DATASOURCES - DATAATTRIBUTES is one to one (one data source per type of data).
- EXTRA SCOPE, already in this ERD (backup plans to widen the scope: the tables or columns exist, but no feature is built on them yet; see AdviseCare_Extra_Scope_List.txt):
  + ES1 Scheduled data ingestion / live integration with FAP, FLM, LMS: DATASOURCES, INGESTIONSCHEDULES, INGESTIONJOBS (and STUDENTDATA.dataSourceId)
  + ES2 Stored report history: REPORTS (case reports, statistics and the student JSON export are generated and downloaded on the fly, not stored)
  + ES3 Backup and restore with integrity check: BACKUPS, RESTOREOPERATIONS
  + ES4 Advisor suggestion algorithm: no extra table needed for a first version; it would score advisors from CASES (familiar advisor-student pair, current caseload), ACCOUNT_SUBJECT and SUBJECTS (specialisation), SUPPORTCATEGORIES (support type) and CASEFEEDBACKS.rating; the Programme Head still decides
  + ES5 Advising effectiveness analysis: no extra table needed, it would use CASES, CASESTAGEHISTORIES, REFERRALS, INTERVENTIONS and CASEFEEDBACKS
  + ES6 Importing accounts and student data from a Google Sheet: no extra table needed, it writes the same ACCOUNTS, ACCOUNT_ROLE, STUDENTPROFILES and STUDENTDATA rows as the Excel/CSV imports
  + ES10 Account import that also updates existing accounts: no extra table needed, it updates ACCOUNTS and STUDENTPROFILES
  + ES12 Anonymised statistics for the other roles (cases, consent, imports, accounts): no extra table needed, same suppression rule as the welfare statistics
- EXTRA SCOPE, not in this ERD (would need new tables or columns):
  + ES7 Advisor availability slots and meeting swaps: advisors publish free time slots that students book, and advisors swap meet-ups with each other (would need an availability table); agreeing a meet-up date is in the current version (MEETUPREQUESTS, MEETUPSCHEDULES)
  + ES8 AI assistance in the case thread (suggested replies or summaries in CASEMESSAGES): needs a way to mark AI-written messages
  + ES9 Accounts without a Google account on file (activation code): ACCOUNTS.email must allow null
  + ES11 Programme of each student: STUDENTPROFILES.programmeId, only needed once there is more than one programme / Programme Head
  + ES13 AI advisor as a backup when there are not enough advisors: an AI account or CASES.advisedBy (human/ai), an AI-suitability score per case and its rules, and AI-written CASEMESSAGES; the Programme Head always decides whether a case is AI-advised
  + ES14 Advisor profile for the suggestion algorithm: e.g. ADVISORPROFILES (expertise, languages, personality/working-style tags, availability) if the team decides those factors are needed
  + ES15 Admin configuration panel (not officially registered in docs): a SYSTEMSETTINGS key/value table (settingKey, settingValue, updatedBy, updatedAt) holding the settings listed in AdviseCare_Functional_Requirements.txt; until then the values are fixed in code/appsettings.json
- Imports and ingestion jobs are all-or-nothing: one invalid row fails the whole import and nothing is written. Transcript PDFs are imported only when every uploaded file is valid (invalid files are removed in the preview first), and a semester or subject code that is not in ACADEMICTERMS / SUBJECTS is an error, as in the Excel/CSV import.
- Transcript import (decided 18/11/2026, changed 20/11/2026): it has no tables of its own. Like the Excel/CSV import it keeps nothing between the preview and the import: the preview reads the PDFs and returns each file's rows and errors, the import reads them again and writes every row to STUDENTDATA in one save (encrypted, insert-only, consent-guarded, per subject, the file name in provenanceNote); its history is the activity log (transcriptImported / transcriptImportFailed). Removed: STUDENTSUBJECTRESULTS (18/11/2026), TRANSCRIPTIMPORTBATCHES and TRANSCRIPTIMPORTFILES (20/11/2026). The printed status (Passed, Exempt, Studying...) is not stored: pass/fail is worked out from Subject mark and Attendance rate.
- STUDENTDATA has no transactionTo/validTo: each row's end time is the transactionFrom/validFrom of the next row for the same student, attribute and term (and subject, for a per-subject attribute).
- Per-subject data attributes (DATAATTRIBUTES.isSubjectSpecific): their values carry STUDENTDATA.subjectId and are kept, shown, compared, corrected and counted per subject; per-term attributes leave subjectId empty. The student data import maps an optional subject column (subject codes): it is required on rows of a per-subject attribute and must be empty on the others. Consent stays per data attribute, so sharing Attendance rate shares it for every subject. No missing rows are made for per-subject attributes, since AdviseCare has no list of the subjects each student takes (a student-subject enrolment table would be needed for that).
- Point-in-time views use either time axis: system time ("what the system knew on date X": the latest row with transactionFrom up to X) or valid time ("what was true on date X by today's knowledge": among rows with validFrom up to X, the latest validFrom, a later transactionFrom winning on ties).
- Bitemporal / history data is create-read-delete only, never updated through the API: STUDENTDATA (except erasure clearing dataValue), CASESTAGEHISTORIES, CONSENTHISTORIES, ACCESSLOGS (except its review fields isFlagged/status), CASENOTES once finalized, CASEMESSAGES and CASEMESSAGEATTACHMENTS (append-only, no edit or delete) and CASE_ATTRIBUTE (what the student offered with a request and why).
- Point-in-time reconstruction ("way back machine") is computed only when an advisor asks for a past date; nothing is precomputed.
- Removed in this version: EVENTCATEGORIES, EVENTS, EVENT_REGISTRATION. Removed columns: CONSENTS.narrowedAt and the "narrowed" consent state (a student shares or withdraws per attribute instead), ACCESSPOLICIES.requiredConsentStatus (only "granted" was left) and ACCESSPOLICIES.isActive / DATASOURCES.isActive (the status enum of the same table already says it).
- INDICATORS was merged into DATAATTRIBUTES (they were one to one) and STUDENTINDICATORS renamed to STUDENTDATA. Archiving a data attribute is one-way: it can no longer be attached to a purpose, granted, requested or imported (import rows for it are rejected and listed, the other rows are still imported), but existing values and consents are kept and still apply.
- Case thread vs case notes (the chat rules, e.g. real-time or not, who else may write and when, are still to be decided; see the Q&A history): CASEMESSAGES is the two-way thread the student of a case and its current advisor both write in (the other side is notified, nothing can be added while the case is closed, a student can write once an advisor is assigned); the Programme Head and referral staff can read it. CASENOTES stay the advisor's records that students never see. CASEMESSAGES replaced CASEADVISORUPDATES (advisor-only updates).
- CASE_ATTRIBUTE records which data attributes the student offered with a support request and an optional note each (shareReason); CASES.requestReason holds only the overall story. Access to the values is still decided by CONSENTS and the access guard, so withdrawing a consent later hides the value even though the CASE_ATTRIBUTE row stays. Cases opened by an advisor (EX3) have no rows.
- Removed in this version as well: ADVISORASSIGNMENTS (advisors are linked to students only through CASES.advisorId) and ASSIGNMENTCHANGEREQUESTS, replaced by CASECHANGEREQUESTS (a change of advisor is requested per case).
- Access guard ("if you consent, we serve"): staff may read a student's attribute only when the student has a granted, unexpired consent on it under a purpose that is active, still covers the attribute (PURPOSE_ATTRIBUTE) and has an active access policy for one of the staff member's roles. Inside a case only the case category's purpose counts; outside a case (e.g. a student's data read outside a case) any such purpose counts, and attributes not consented are simply left out. A consent is given to everyone holding a role that has a policy for the purpose, not to one named advisor, so the guard does not check which advisor is asking (by design). Every allowed read writes one ACCESSLOGS row per attribute; students reading their own data are not logged.
- Correction requests work like a case for one data attribute, but never open a case: the student picks the wrong STUDENTDATA row and a consent purpose that covers its attribute; the request grants (or keeps) the student's CONSENTS row for that attribute under that purpose, which is what lets an advisor read the value for the review. Every advisor whose role has an active access policy for that purpose sees the pending request in their own correction request list (a shared pool, shown separately from cases); the first one to approve or reject it is stored in reviewedBy. No open case is needed. An approved request inserts a new STUDENTDATA row (status = correction) with the same validFrom as the wrong row; the wrong row stays, so system time still shows the old value and valid time shows the corrected one.
- Case workflow: every stage change and every hand-over writes a CASESTAGEHISTORIES row (a hand-over, i.e. a direct reassignment or an approved CASECHANGEREQUESTS row, has the same stage on both sides). A pending referral blocks stage changes, reassignment and approving a change request. A Welfare Officer who accepts a referral does not take the case (advisorId unchanged, stage stays referred); a returned referral puts the case back to the stage it had before, with the reason in CASESTAGEHISTORIES.reason.
- Meet-ups (added 24/11/2026, Q-271, QC-272; owner Member B): while a case is not closed and is in stage contacted or followUp, its student or its current advisor requests a meet-up (MEETUPREQUESTS: date, start time and a flexible duration, location, optional room, reason; one pending request per case). Only the side that did not propose the current date answers: accept, change the date (the same row is updated, proposedBy becomes that side, rescheduleCount + 1, and it goes back to the other side) or deny with a reason; the side who proposed the current date can withdraw it. Accepting creates a MEETUPSCHEDULES row and, if the case is in contacted, moves it to followUp with a CASESTAGEHISTORIES row (in followUp further meet-ups change no stage). Times: Monday to Friday, Vietnam time 08:30-11:30 and 13:30-18:00, 15-minute steps, at least 15 minutes, inside one window, in the future; a time that overlaps a scheduled meet-up of the same advisor or student is refused. Either side cancels a scheduled meet-up with a reason before it starts; the advisor marks it completed or missed once it has started. Closing a case or changing its advisor (reassignment, approved case change request, accepted referral to another advisor) cancels its pending requests and its scheduled meet-ups that have not started. The advisor's schedule screen shows each scheduled, completed or missed meet-up as a block in those windows. Meet-ups are case records (visible to the people working on the case, not consent-based, not written to ACCESSLOGS). Old tables 28-49 became 30-51.
- Early-support indicators: the Steward defines INDICATORS (a rule on one data attribute: comparison + threshold, with a severity, the case priority and a support category). After every student data import (and when a rule is activated or changed) the server compares each enrolled student's latest value per term (per term and subject for a per-subject attribute) with every active rule and raises an INDICATORFLAGS row for each hit (one open flag per student, rule, term and subject; the subject is empty for a per-term rule); a later value that no longer hits the rule clears an open flag. Raising a flag reads the value inside the server only, so it is not an access by a person and writes no ACCESSLOGS row. Staff see the flag (student directory data, rule name and description, severity, priority, term, subject) but never the value: the value stays behind the access guard until the student consents (consent request or support case). The Programme Head works through the flag queue (severity, then priority, then oldest) and either opens a case from a flag for an advisor of the rule's support type (CASES.openedBy = the Programme Head, priority from the rule, the flag's caseId set) or dismisses it with a reason; an advisor can ask to take a flagged student on (status requested, requestedBy), which the Programme Head approves (case opened for that advisor) or turns down (flag back to open). Cases are still never opened automatically.
- Case feedback: after a case is closed its student may rate it once (CASEFEEDBACKS, 1-5 stars and an optional comment); the rating stays tied to the advisor who handled the case. Who may read feedback (the advisor, the Programme Head, anonymous or not) is still to be decided with Member D.
- Welfare statistics and cohort data (anonymised, counts and averages only): welfare statistics count referred cases, interventions, support grants, external referrals and escalations per period, category and faculty, and hide every cell counted from fewer than 5 different students. Cohort data averages a numeric attribute (or counts each value of a categorical/boolean one) per term and/or faculty using only values the student consented to under the purpose marked CONSENTPURPOSES.isForStatistics, decrypts each value only after the access guard allows it, logs the reads as one ACCESSLOGS row per value, uses the latest value per student/attribute/term (in one chosen subject for a per-subject attribute), never counts emergency access, and hides every cell with fewer than 10 different students.
- Consent expiry is checked when data is read (no background job): a granted consent past expiresAt gives no access until the student renews it.
- Erasure: ATTRIBUTEKEYS holds one key per student per attribute, so withdrawing a consent queues an ERASUREREQUESTS row only when the attribute is no longer granted under any purpose and the student has an active key for it; the Steward executes it in one save: the key is destroyed (wrappedKey null, status = destroyed) and every STUDENTDATA value and CORRECTIONREQUESTS value under that key is cleared (erasedAt set). A backup taken before the erasure still holds the old wrapped key, so before restoring one the completed erasures must be re-applied (until the master key version it used is deleted).
- Emergency access: Stewards share one pool of requests; the first Steward to approve or reject is stored in stewardId (a rejection needs a rejectionReason). While approved and before scopeExpiresAt, the requester may read every attribute of that student through the access guard; each read is logged with consentPurposeId = null. The access ends on its own at scopeExpiresAt.
- Encryption (envelope encryption, AES-256-GCM): the master keys live only in server configuration (Encryption:MasterKeys, numbered versions, plus Encryption:CurrentVersion). Each student/attribute key in ATTRIBUTEKEYS is wrapped with a key derived (HKDF) from one master key version and that row's ids, and its masterKeyVersion is stored. Each value in STUDENTDATA/CORRECTIONREQUESTS is encrypted with that key and tied to key, student, attribute, row and field. Users never receive a key: the server decrypts in memory only after the access guard allows the read, and API responses are sent with Cache-Control: no-store. Withdrawing a consent stops access at the guard at once; erasure is the later step that makes the stored values unreadable to everyone. Rotation: a new master key version is added, the Steward rewraps every active key (values are not re-encrypted), and an old version is deleted from the configuration once no kept database backup still needs it, after which erased values are unrecoverable from those backups too. Losing every copy of a master key makes its values unreadable, so each version is kept by two team members offline and only in the hosting's environment variables.
- Student data comes in three kinds, each with its own access rule:
  + Directory data: email, fullName, userName, faculty (ACCOUNTS) and studentCode, academicStatus (STUDENTPROFILES). Supplied by the school through the account import; every staff role (including every advisor) may read it at any time, with no consent and no access log, since the app cannot route or handle a case without it.
  + Data attributes (values in STUDENTDATA, defined by DATAATTRIBUTES): everything else that describes or measures the student. Readable only through the access guard (consent), and every read is logged in ACCESSLOGS, even when consent was given.
  + Case records (CASES, CASE_ATTRIBUTE, CASEFEEDBACKS, CASEMESSAGES, CASEMESSAGEATTACHMENTS, MEETUPREQUESTS, MEETUPSCHEDULES, CASENOTES, INDICATORFLAGS, CASESTAGEHISTORIES, REFERRALS, INTERVENTIONS, SUPPORTGRANTS, EXTERNALREFERRALS, ESCALATIONS): visible to the people working on the case; not consent-based and not written to ACCESSLOGS.
- STUDENTPROFILES exists only for Student accounts; it is created in the same save as the account (account import, single create, or giving the Student role) and only the admin edits it. The account import (.xlsx or .csv) has 5 filled columns for staff rows (email, fullName, userName, facultyCode, role) and up to 7 for Student rows (+ studentCode, and academicStatus, which means enrolled when left empty).
- Each account has exactly one role (ACCOUNT_ROLE holds one row per account): a Student account never also holds a staff role, a staff account never becomes a Student account, and staff move from one staff role to another instead of collecting several.
- Usually one Programme Head for the whole app (the manager), but the system allows more. PROGRAMMES is kept but not used by other tables for now.
