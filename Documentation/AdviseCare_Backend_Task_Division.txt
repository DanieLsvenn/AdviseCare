MEMBER A - IDENTITY, ACCOUNTS, MASTER DATA, NOTIFICATIONS
Tables owned: ACCOUNTS, STUDENTPROFILES, ROLES, ACCOUNT_ROLE, SESSIONS, ACTIVITYLOGS, NOTIFICATIONS, NOTIFICATIONPREFERENCES, FACULTIES, PROGRAMMES, ACADEMICTERMS, SUBJECTS, ACCOUNT_SUBJECT
==========

A1. Authentication and sessions (AuthController; AccountService + SessionService)
A1.1. Account linking: emailed one-time link + Google sign-in; token checked by its SHA-256 hash (7-day expiry), Google email must match, the Google account must not be used by another account; store googleId, linkStatus = linked, sign the user in
A1.2. Sign in with Google: only accounts already linked (matched by googleId); any other Google account is refused
A1.3. Sign in with email/username + password; refuse deactivated/banned accounts
A1.4. JWT with accountId, sessionId and roles; a session lasts 1 month
A1.5. Forgot password / reset by email (Gmail SMTP): linked accounts only, token stored hashed (1-hour expiry), the reset logs out every session
A1.6. Set or change password with one endpoint: the old password is asked only when one already exists; the other sessions are logged out. The password step after linking can be skipped
A1.7. Sessions: record device, list own sessions, log out, log out of other sessions, automatic end after 1 month
A2. Account management (Admin; AccountsController, RolesController)
A2.1. Account CRUD: get all (paged), get by id, search/filter (role, faculty, student code, academic status, link status, account status), create a single account (email, fullName, userName, faculty, roles, plus studentCode and academicStatus for a Student), update details (changing the email unlinks the Google account)
A2.2. Bulk import from an Excel file (email, fullName, userName, facultyCode, role, studentCode, academicStatus): 5 filled columns for staff rows, 7 for Student rows; validate all rows, all-or-nothing (Google Sheet import is future, FU6; updating existing accounts through the import is future, FU10)
A2.3. Send / resend account-linking emails, linkStatus notLinked -> emailSent
A2.4. Roles CRUD and account roles (ACCOUNT_ROLE); the last System Administrator role cannot be removed
A2.5. Activate/deactivate, ban/unban (never on the admin's own account; ends all active sessions)
A2.6. Student profiles (STUDENTPROFILES): created in the same save as a Student account (single create, import, or giving the Student role, which then needs studentCode and academicStatus); directory data viewable by all staff without consent or logging (StudentProfilesController: GET by studentId, search; GET me for the student); the admin edits studentCode and academicStatus (PUT /api/StudentProfiles/{studentId}); shown in the account responses too
A3. Master data (Admin)
A3.1. Faculties, programmes and academic terms CRUD; only one term can be current, setting a new current term moves the old one to past
A3.2. Subjects under a faculty CRUD; link academic advisors to subjects (ACCOUNT_SUBJECT)
A4. Notifications (in-app; NotificationService)
A4.1. Notification CRUD; own inbox: list, mark read, mark all read, delete, clear old (read) notifications
A4.2. NotifyAsync for other features: writes the in-app notification and, if the account's email preference is on, also sends it by email
A4.3. Notification preferences (email / in-app); a missing row means the channel is on
A5. Own account: profile (username, preferred language), avatar upload (Supabase Storage), activity history (ACTIVITYLOGS, types listed in AdviseCare_Activity_Types.txt)
A6. Admin configuration panel (not officially registered in docs; not started): the settings listed in AdviseCare_Functional_Requirements.txt, needs a SYSTEMSETTINGS table

MEMBER B - CONSENT AND DATA PROTECTION
Tables owned: DATAATTRIBUTES, CONSENTPURPOSES, PURPOSE_ATTRIBUTE, ACCESSPOLICIES, CONSENTS, CONSENTHISTORIES, CONSENTREQUESTS, ACCESSLOGS, EMERGENCYACCESSREQUESTS, ERASUREREQUESTS, ATTRIBUTEKEYS
==========

B1. Steward configuration
B1.1. Data attributes (the student data that is only shown with consent): name, description, data type (numeric/categorical/boolean); archive (one-way)
B1.2. Consent purposes: create (starts inactive), attach/remove attributes, activate/deactivate, retire
B1.3. Access policies: role + purpose (draft -> active -> revoked, no edit once active); test a policy against a sample student
B2. Access guard (IAccessGuardService, used by Member C for every student data, point-in-time and correction read)
B2.1. Decide access: granted, unexpired consent + purpose active and still covering the attribute + active policy for one of the accessor's roles ("if you consent, we serve"); the case category's purpose inside a case, any purpose outside a case
B2.2. Return "exists, not shared" instead of the value when access is refused (inside a case); leave the attribute out of student lists
B2.3. Write every access to ACCESSLOGS (one row per value read, with its studentDataId; batch writes with LogAccessAsync's batch form); the student's own reads are not logged
B3. Student consent
B3.1. List purposes and their attributes; grant, withdraw (single attribute or whole purpose), change expiry; consent history rows
B3.2. Consent requests from advisors (with the purpose): create, edit pending, respond (grant/deny), withdraw pending
B3.3. Consent expiry check (when data is read)
B4. Encryption and erasure
B4.1. Envelope encryption: one key per student per attribute (ATTRIBUTEKEYS), AES-256-GCM; versioned master keys from configuration (Encryption:MasterKeys + Encryption:CurrentVersion), the version used is stored in ATTRIBUTEKEYS.masterKeyVersion; each wrapping key is derived with HKDF from the master key and the key row (attributeKeyId, studentId, dataAttributeId), so a wrapped key cannot be moved to another row; values stored as VARBINARY (format byte, nonce, tag, ciphertext) bound to their row and field; IAttributeKeyService.EncryptValuesAsync / DecryptValuesAsync used when STUDENTDATA and CORRECTIONREQUESTS values are written/read; Steward can list key status (never the key) and rewrap keys after a master key rotation (PUT /api/AttributeKeys/rewrap)
B4.2. Withdrawal queues an erasure request; Steward verifies and executes it (destroy key, clear the encrypted STUDENTDATA and CORRECTIONREQUESTS values, set erasedAt, all in one save), audit trail kept
B5. Access log and processing records
B5.1. Search/filter access log; flag entries; Steward review (cleared / confirmed issue)
B5.2. Student's own access log
B5.3. Export processing record for one student or a date range
B6. Emergency access (pending review): request, approve with time limit, reject with a reason, auto-expire; Stewards share one pool, the first to act is stored as stewardId; the access guard allows an approved, unexpired request (logged with consentPurposeId = null)

MEMBER C - STUDENT DATA, PROFILE AND WELFARE
Tables owned: STUDENTDATA, CORRECTIONREQUESTS, INTERVENTIONS, SUPPORTGRANTS, EXTERNALSERVICES, EXTERNALREFERRALS, ESCALATIONS
(DATASOURCES, INGESTIONSCHEDULES, INGESTIONJOBS are future: no work now)
==========

C1. Student data import (Admin; StudentDataController)
C1.1. Upload Excel/CSV (Google Sheet is not built yet); preview the header and sample rows; map columns to data attributes
C1.2. Validate the whole file (also as a dry run), all-or-nothing; return the list of invalid rows; rows of archived data attributes are not imported but listed in rejectedRows, and the rest still goes in
C1.3. Insert new STUDENTDATA rows only (dataSourceId null, provenanceNote = file name + import date); never update; encrypt each value with Member B's IAttributeKeyService.EncryptValuesAsync before saving (new keys are saved by the same SaveAsync)
C1.4. Flag missing values (isMissing) for every enrolled, active student without a value for an imported attribute and term
C1.5. Import history through ACTIVITYLOGS
C2. Student data and history
C2.1. Student data API: data attribute values with sources and missing-data notices, inside a case (the case category's purpose, only the case's advisor) or outside a case (any purpose the staff role has a policy for, or emergency access); every value passed through Member B's access guard (IAccessGuardService, then IAttributeKeyService.DecryptValuesAsync and LogAccessAsync for each value shown; an erased value is shown as erased)
C2.2. Point-in-time view ("way back machine") on both time axes: system time (latest transactionFrom up to the chosen date) and valid time (latest validFrom up to the chosen date, a later recording winning on ties); compare two dates
C2.3. Student's own data view (no consent needed, not logged)
C2.4. Student JSON export (own record + own access log), generated on the fly
C2.5. Correction requests (pending review): submit on one STUDENTDATA row (values stored encrypted), reviewed by the advisor of one of the student's open cases (the values are only shown with consent or emergency access, and logged), approved = new "correction" row with the same validFrom, withdraw
C3. Welfare (Student Welfare Officer)
C3.1. Interventions: log, update until closed (the outcome is part of the update), close, history per student
C3.2. Support grants under an intervention; revoke
C3.3. External services list; external referrals with follow-up due date, follow-up outcome, close, overdue flag (background check)
C3.4. Escalations: officer raises, Programme Head responds, status tracking
Note: welfare works on existing CASES rows (from the seed data), so it does not wait for Member D's case APIs

MEMBER D - SUPPORT REQUESTS, CASES, MATCHING AND REPORTS
Tables owned: SUPPORTCATEGORIES, CASES, CASENOTES, CASESTAGEHISTORIES, REFERRALS, CASECHANGEREQUESTS
==========

D1. Support categories (Admin): create/edit/archive, academic/wellbeing, governing consent purpose
D2. Support requests (Student)
D2.1. Create a case: support type, category, subject (academic), reason
D2.2. List the attributes the student may share (from the category's purpose) and record the chosen ones as consents (calls Member B's consent table directly through the DbContext, or B's service once ready)
D2.3. Student's own cases, stages and history
D3. Matching (Programme Head)
D3.1. Queue of unassigned cases
D3.2. Suggested advisors: by type, subject specialisation, faculty, workload (an advisor already handling another open case of the student first is optional)
D3.3. Assign a case: set advisorId (the case's advisor is the only advisor-student link), notify student with the advisor's contact information (NotificationService.NotifyAsync, Member A)
D3.4. Reassign directly
D4. Advisor case workflow (Academic and Wellbeing Advisors)
D4.1. Assigned case list: sort, filter, unread count
D4.2. Advisor opens a case for a student based on their data (read through Member C's StudentData API)
D4.3. Case notes: draft, edit, finalize (no edits after finalize)
D4.4. Stage changes with reason (CASESTAGEHISTORIES insert-only); close, reopen
D4.5. Referrals: to another advisor (same/other type) or to the Welfare Officer; accept / return
D5. Case change requests (CASECHANGEREQUESTS): the case's advisor or student requests another advisor for one case, Programme Head approves (CASES.advisorId = proposed advisor) or rejects
D6. Reports (Programme Head): cases in a time range with filters, caseload volume and closure time per advisor, export Excel/CSV/PDF generated on the fly
