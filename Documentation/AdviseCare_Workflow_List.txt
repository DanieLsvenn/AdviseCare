ADVISECARE WORKFLOWS (current version)

Actors: System Administrator (Admin), Data Protection Steward (Steward), Academic Advisor, Wellbeing Advisor, Student Welfare Officer (Welfare Officer), Student, Programme Head (usually one for the whole app, the manager; the system allows more)
External: Google (personal account sign-in), Email service, External Support Services

MEMBER C IMPLEMENTATION CHECKPOINTS
===================================

Member C work is split into independently reviewable/pushable checkpoints. Proceed one checkpoint at a time and request approval before starting the next:
- C-01 External service read API: list, get by id, and filter the catalogue (implemented).
- C-02 External service catalogue writes: create/update (System Administrator only; Welfare Officers have read access; implemented).
- C-03 External referrals and follow-up, including overdue detection (uses existing CASES and EXTERNALSERVICES; implemented).
- C-04 Welfare escalations (uses existing CASES; implemented).
- C-05 Interventions and support grants (uses existing CASES; implemented).
- C-06a Indicator import file preview, column mapping, and whole-file validation for .xlsx/.csv (implemented; no data is written).
- C-06b1 Authenticated AES-256-GCM envelope encryption and per-student/attribute Vault Transit key provisioning (implemented; Vault keys enable deletion, DEKs are wrapped by Transit, and HMAC subkeys are HKDF-derived).
- C-06b2 Insert-only indicator persistence, missing flags, StudentProfile provisioning, studentCode resolution, and import activity logging (implemented; imports are all-or-nothing and missing rows cover all active Student-role accounts for each imported indicator/term pair).
- C-07a Authorized advisor indicator-profile reads, consent-gated decryption, and per-value access logging (implemented; assigned-case advisor only; optional term filter).
- C-07b Point-in-time indicator history and comparison (implemented; reconstructs system knowledge through the end of the selected UTC date; each snapshot uses C-07a access checks and logging).
- C-07c Student own-profile access and JSON export (implemented; self-only profile, current indicator values, own cases and own access log; export recorded in ACTIVITYLOGS).
- C-08 Correction requests (implemented; each request has a composite FK to its exact student-indicator row, encrypted before/after values, assigned-advisor review, and insert-only correction history).
- C-09 Anonymised welfare statistics (implemented; cases grouped by support category for one academic term or a complete UTC date range; categories with fewer than five distinct students are suppressed; Welfare Officer-only CSV export is generated on demand and activity-logged).
- C-08 runtime verification (passed on 2026-10-25 against the v6 development database and local Vault Transit dev server; the temporary fixture remains for inspection; see [Member C changes and runtime validation](./Member_C_Changes_and_Runtime_Validation.md)).
- Startup fixes confirmed during runtime verification: Studentprofile has its EF primary-key mapping, DI-provided database options are preserved, and Vault Transit keys are configured for deletion after creation.

==========
MAIN WORKFLOWS
==========

WF1: Admin creates accounts
1. Admin signs in with the admin account
2. Out of scope: the school collects students' information itself (e.g. through a Google Form). We assume the Admin already has the list of students/staff and their personal Gmail addresses
3. Admin chooses how to create accounts
3.1. Bulk import
3.1.1. Admin uploads an Excel file containing email, fullName, userName, facultyCode and role (importing from a Google Sheet is future, see FU6)
3.1.2. System validates every row (required fields, email format, duplicate email/username in the file or in the system, faculty code exists, role exists)
3.1.3. If any row is invalid, nothing is created and the system shows the invalid rows (all-or-nothing)
3.1.4. If all rows are valid, the system creates the accounts (no password yet, linkStatus = notLinked, role taken from the file)
3.2. Single account
3.2.1. Used for special cases (late or off-term enrolment, students who missed the school's survey, staff accounts)
3.2.2. Admin fills in email, fullName, userName, faculty and role
3.2.3. System creates the account (no password yet, linkStatus = notLinked)
4. System prompts the Admin to send account-linking emails to the newly created accounts
4.1. Admin confirms
4.2. System emails each account a one-time linking link (only a hash of the token is stored in resetToken, valid for 7 days) and sets linkStatus = emailSent
5. (User side, see EX1) the user opens the link, signs in with the personal Google account, the account becomes linked and the user sets a password or skips it
6. Admin views the account dashboard
6.1. Sort/filter accounts by role, faculty, link status or account status
6.2. Resend the linking email to accounts still in emailSent
6.3. Open an account to edit its details or roles, deactivate or ban it (see EX12)

WF2: Student requests support and gets advised
1. Student signs in
2. Student opens "Request support" and creates a new case
2.1. Chooses the support type: academic or wellbeing
2.2. Chooses the category
2.2.1. Academic: the subject (dropdown) and the topic (e.g. course content, study plan, FLM/FAP/LMS usage)
2.2.2. Wellbeing: the issue (e.g. mental health, accommodation, family, money)
2.3. Writes the reason
2.3.1. The reason is visible to the authorized case team by default; the backend must enforce the selected visibility scope
2.4. Chooses which data attributes to share
2.4.1. Only the attributes covered by the category's consent purpose are offered (defined by the Steward)
2.4.2. The student may leave it empty
2.4.3. Each chosen attribute is recorded as consent for that purpose
2.5. Submits; the case is created with stage = pending
3. Programme Head matches the case (manual for now)
3.1. Programme Head sees the case in the matching queue
3.2. Programme Head picks a suitable advisor
3.2.1. Academic case: an academic advisor specialised in that subject, or a general academic advisor of the student's faculty
3.2.2. Wellbeing case: a wellbeing advisor
3.2.3. If the student already has an assigned advisor of that type, that advisor is preferred (quality-of-life add-on, optional: familiar advisor-student pairs first)
3.3. System sets the case's advisor, records the advisor assignment and moves the case to stage = assigned
4. System notifies both sides
4.1. Student receives the advisor's contact information by email and in-app notification
4.2. Advisor receives a notification of the new case
5. Advisor reviews the case
5.1. Opens the case: reason, category, subject
5.2. Opens the student profile: only consented data is shown, with its source and missing-data notices
5.3. If more data is needed, the advisor sends a consent request (see EX7)
6. Advisor and student meet
6.1. They decide by themselves when and how to meet (online, offline, external messaging app); the app has no scheduling system for now
6.2. Advisor moves the case to stage = contacted
7. Advisor records case notes (discussion, agreed actions), selects assignedAdvisor or caseTeam visibility, and finalizes them; the API enforces the audience on reads and referrals
8. If the case needs someone else
8.1. Advisor refers it to another advisor of the same or the other type (see EX4)
8.2. Wellbeing Advisor refers money matters to the Welfare Officer (see WF2b)
9. Advisor follows up (stage = followUp) and closes the case (stage = closed)
10. Every stage change is recorded in the case's stage history

WF2b: Welfare Officer handles a financial referral (continuation of WF2 step 8.2)
1. Welfare Officer sees the referral in the incoming queue
2. Welfare Officer triages it
2.1. Opens the referral and the advisor's notes
2.2. Sets the priority
2.3. Accepts it, or returns it to the advisor with a reason
3. Welfare Officer works with the student (loan arrangement, financial aid, banking documents)
3.1. Logs each intervention (type, date, notes)
3.2. Records any support grant issued
3.3. Records the outcome
3.4. Reviews intervention history for the student
4. If an outside service is needed (e.g. a money-lending service, a bank)
4.1. Welfare Officer reads the external services catalogue; only active services are selected for new referrals
4.2. System Administrator creates or updates catalogue entries (Welfare Officers cannot write to the catalogue)
4.3. Welfare Officer records the external referral with an expected follow-up date
4.4. System flags it as overdue if the date passes without an outcome
4.5. Welfare Officer logs the follow-up outcome
5. If the case goes beyond the Welfare Officer's authority, it is escalated (see EX5)
6. Welfare Officer closes the intervention; the case's assigned advisor is notified to continue follow-up and closure

WF3: Steward sets up consent
1. Steward signs in
2. Steward defines the shareable data
2.1. Creates an indicator together with its data attribute (name, description shown to students, data type)
2.2. Archives indicators/attributes that are no longer used (one-way; existing values and consents are kept)
3. Steward defines consent purposes
3.1. Creates a purpose (e.g. Academic advising, Wellbeing support, Financial support); it starts inactive
3.2. Attaches the data attributes the purpose covers (an attribute can belong to several purposes)
3.3. Activates the purpose
4. Steward configures access policies
4.1. Links a role to a purpose (the policy starts as a draft; the student's consent must be granted)
4.2. Activates the policy
4.3. Tests the policy against a sample case
5. Admin links each support category to the purpose that governs it (see EX11), so students only see the matching attributes when they request support
6. Later changes: a purpose is retired (never deleted) when no longer used; policies are revoked rather than edited

WF4: Programme Head lists, reports and exports
1. Programme Head signs in and opens the reports page
2. Chooses a time range
3. Filters by advisor, support type, category, subject or stage
4. Views the result
4.1. List of cases/consultations in the range
4.2. Caseload volume per advisor
4.3. Average time to close a case per advisor
5. Exports the list/report (Excel/CSV/PDF)

WF5: Admin imports student indicator data
1. Admin signs in and opens "Import indicator data"
2. Admin uploads an .xlsx/.csv file; Google Sheet import remains pending its integration setup
3. Admin maps file columns to indicators (student identifier, indicator, value, term, date)
4. System previews the file and validates the whole file without persisting rows (C-06a)
4.1. If any row is invalid, nothing is imported and the system lists the invalid rows (all-or-nothing)
4.2. If all rows are valid, C-06b2 inserts new STUDENTINDICATORS rows only (dataSourceId null, provenanceNote includes file name and import date); C-06b1 supplies authenticated ciphertext and HMAC using the student's per-attribute key
5. C-06b2 inserts an isMissing row for every active Student-role account missing each indicator/term pair represented in the import; missing-row validFrom is the term start date
6. C-06b2 writes import activity history in the same database save and returns inserted/missing row counts
7. Note: C-06b1 authenticated encryption/key provisioning, C-06b2 import persistence, C-07, and C-08 are implemented; C-08 has passed manual runtime verification. The next Member C checkpoint has not started and requires user approval. Scheduled automatic ingestion (data sources, schedules, jobs) is future work (see AdviseCare_Future_List.txt)

EXTRA WORKFLOWS
==========

EX1: Account linking and first sign-in
1. User opens the account-linking email
2. User clicks the one-time link
2.1. If the link has expired, the user is told to ask the Admin to resend it
3. User signs in with the personal Google account
3.1. System checks the Google email matches the account email
3.2. System checks no other account is already linked to this Google account
3.3. System stores the Google id, sets linkStatus = linked, clears the token and signs the user in
4. Account setup step: the system offers to set a password right away, with a Skip button and the note "You can set a password in Settings"
5. User sets the preferred language
6. User lands on the home page of their role
7. Later sign-ins: "Sign in with Google" or email/username + password ("Sign in with Google" refuses any Google account that is not linked to an account)

EX2: Sign in, forgot password and sessions
1. User signs in with Google or with password
2. System checks the account status (deactivated or banned accounts are refused)
3. System opens a session and records the device; a session ends on its own 1 month after sign-in
4. Forgot password
4.1. User enters the email (only linked accounts get a reset link, valid for 1 hour; the reply is the same either way)
4.2. System emails a one-time reset link
4.3. User sets a new password; every session of the account is logged out
5. User sets or changes the password in Settings (the old password is asked only if one already exists); the other sessions are logged out
6. User views active sessions and logs out of other sessions

EX3: Advisor reaches out based on indicators
1. Advisor views indicators of the students assigned to them (only consented data: "if you consent, we serve", attributes a student has not shared are left out)
2. Advisor notices a student who needs help (merits, attendance, grades...)
3. Advisor opens a case for that student with a reason and category
4. System notifies the student that the advisor wants to meet, with the advisor's contact information
5. Continues as WF2 from step 5

EX4: Referral between advisors
1. Advisor opens the case and chooses "Refer"
2. Advisor picks the receiver (advisor of the same or the other type) and writes the reason and priority
3. Receiver gets a notification
4. Receiver accepts (becomes the handling advisor) or returns the referral with a reason
5. Case stage history records the hand-over

EX5: Escalation to the Programme Head
1. Welfare Officer marks the case for escalation and writes the reason
2. Programme Head gets a notification
3. Programme Head records a response/decision
4. Welfare Officer sees the response and continues the case

EX6: Advisor assignment change
1. Advisor (or student through the advisor) requests a change of the assigned advisor, proposing a new advisor and a reason
2. Programme Head reviews the request
3. Programme Head approves or rejects it
3.1. Approved: the old assignment is revoked and a new one is created for the proposed advisor
3.2. Rejected: the reason is recorded
4. Both advisors and the student are notified
5. Programme Head can also reassign directly without a request

EX7: Advisor asks for more data (consent request)
1. Advisor picks the student, the purpose and the data attribute needed
2. Advisor states the purpose
3. Student gets a notification and grants or denies
3.1. Granted: a consent record is created under the request's purpose and the advisor can now see the value
3.2. Denied: the advisor sees the attribute as "exists, not shared"
4. Advisor can withdraw a request that is still pending

EX8: Student manages consent and erasure
1. Student opens the consent page and sees each purpose and its attributes
2. Student grants or withdraws consent per purpose, or withdraws single attributes of a purpose
3. Every change is recorded in consent history
4. On withdrawal
4.1. Access is blocked immediately
4.2. An erasure request is queued (when the attribute is no longer shared under any purpose and values are stored)
4.3. Steward verifies the withdrawal; SQL removes live ciphertext/HMAC, Vault Transit destroys the per-attribute key, and SQL records completion only after the KMS call succeeds
4.4. The values become unreadable; the audit trail stays
4.5. Student is notified

EX9: Access log review
1. Every time staff open student data, the system checks role + purpose + consent and logs the access
2. Student views own access log and may flag an entry
3. Steward searches/filters the access log, reviews flagged entries and exports processing records

EX10: Emergency access (pending review)
1. Staff requests access beyond consent with a justification
2. A Steward approves with a time limit, or rejects (Stewards share one pool of requests; the first to act decides)
3. Access ends automatically when the time limit passes; every access is logged

EX11: Master data setup
1. Admin manages academic terms (create, edit, set status; only one term can be current)
2. Admin manages faculties and subjects (subjects belong to a faculty)
3. Admin links academic advisors to the subjects they specialise in
4. Admin manages support categories (name, academic/wellbeing, governing consent purpose)

EX12: Account management
1. Admin opens an account from the dashboard
2. Admin edits the account details (email, full name, username, faculty); changing the email unlinks the Google account and the linking email has to be sent again
3. Admin adjusts roles (the last System Administrator role cannot be removed)
4. Admin deactivates/activates or bans/unbans the account (not their own account)
5. Deactivating or banning ends all active sessions of the account

EX13: Point-in-time reconstruction ("way back machine")
1. Advisor opens a student and clicks "View as of date"
2. Advisor picks the date
3. System rebuilds the record from the latest row per indicator/term recorded by the system through the end of that UTC date (only computed on request; each snapshot applies case-based consent checks and logs each permitted value)
4. Advisor can compare two dates; the access is logged

EX14: Student exports own record
1. Student opens account settings and chooses "Export my data"
2. Student can view their own profile; no case assignment or consent is required
3. System builds a JSON file with the student's identity, current indicator profile, own cases and own access log
4. Student downloads it; the export is logged in ACTIVITYLOGS

EX15: Correction request
1. Student selects a value believed to be wrong and explains why
2. Advisor reviews it against its source
3. Approved: a corrected value is stored as a new version (the old one stays in history); Rejected: the advisor writes the reason
4. Student is notified

EX16: Notifications, language and settings
1. User views notifications, marks them read, clicks through to the item and clears old ones
2. User sets notification preferences (email/in-app)
3. User switches language (Vietnamese/English); the choice is remembered
4. User views own activity history and edits account settings (username, avatar)

EX17: Welfare Officer views anonymised welfare statistics
1. Welfare Officer selects one academic term or a complete UTC calendar-date range
2. System counts cases by support category using the case opened date; categories represented by fewer than five distinct students are suppressed
3. Welfare Officer views the category, case count, and distinct-student count; no student-level rows or overall total are shown
4. Welfare Officer can download the same aggregate results as a generated CSV file
