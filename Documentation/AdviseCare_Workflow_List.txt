ADVISECARE WORKFLOWS (current version)

Actors: System Administrator (Admin), Data Protection Steward (Steward), Academic Advisor, Wellbeing Advisor, Student Welfare Officer (Welfare Officer), Student, Programme Head (usually one for the whole app, the manager; the system allows more)
External: Google (personal account sign-in), Email service, External Support Services

==========
MAIN WORKFLOWS
==========

WF1: Admin creates accounts
1. Admin signs in with the admin account
2. Out of scope: the school collects students' information itself (e.g. through a Google Form). We assume the Admin already has the list of students/staff and their personal Gmail addresses
3. Admin chooses how to create accounts
3.1. Bulk import
3.1.1. Admin uploads an .xlsx or .csv file containing email, fullName, userName, facultyCode, role, studentCode and academicStatus (importing from a Google Sheet is extra scope, see ES6)
3.1.1.1. Staff rows fill the first 5 columns and leave studentCode and academicStatus empty
3.1.1.2. Student rows also fill studentCode (unique, issued by the school) and academicStatus (enrolled/onLeave/withdrawn/graduated; empty means enrolled)
3.1.2. System validates every row (required fields, email format, duplicate email/username/studentCode in the file or in the system, faculty code exists, role exists, the 2 student columns filled for Student rows and empty for every other row)
3.1.3. If any row is invalid, nothing is created and the system shows the invalid rows (all-or-nothing)
3.1.4. If all rows are valid, the system creates the accounts (no password yet, linkStatus = notLinked, role taken from the file), and a student profile (studentCode, academicStatus) for every Student account, in the same save
3.2. Single account
3.2.1. Used for special cases (late or off-term enrolment, students who missed the school's survey, staff accounts)
3.2.2. Admin fills in email, fullName, userName, faculty and role, plus studentCode and academicStatus for a Student account
3.2.3. System creates the account (no password yet, linkStatus = notLinked), with its student profile for a Student account
4. System prompts the Admin to send account-linking emails to the newly created accounts
4.1. Admin confirms
4.2. System emails each account a one-time linking link (only a hash of the token is stored in resetToken, valid for 7 days) and sets linkStatus = emailSent
5. (User side, see EX1) the user opens the link, signs in with the personal Google account, the account becomes linked and the user sets a password or skips it
6. Admin views the account dashboard
6.1. Sort/filter accounts by role, faculty, student code, academic status, link status or account status
6.2. Resend the linking email to accounts still in emailSent
6.3. Open an account to edit its details or roles, deactivate or ban it (see EX12)
6.4. Open a Student account to edit its student profile (studentCode, academicStatus), e.g. when the student goes on leave or graduates (see EX12)

WF2: Student requests support and gets advised
1. Student signs in
2. Student opens "Request support" and creates a new case
2.1. Chooses the support type: academic or wellbeing
2.2. Chooses the category
2.2.1. Academic: the subject (dropdown) and the topic (e.g. course content, study plan, FLM/FAP/LMS usage)
2.2.2. Wellbeing: the issue (e.g. mental health, accommodation, family, money)
2.3. Writes the reason
2.4. Chooses which data attributes to share
2.4.1. Only the attributes covered by the category's consent purpose are offered (defined by the Steward)
2.4.2. The student may leave it empty
2.4.3. The student may add a short note to each chosen attribute on why it matters to the request
2.4.4. Each chosen attribute is recorded as consent for that purpose and, with its note, on the case
2.5. Submits; the case is created with stage = pending and priority = medium (the student does not set the priority)
3. Programme Head matches the case (manual; an advisor suggestion algorithm is extra scope, see ES4)
3.1. Programme Head sees the case in the matching queue (cases can also start from an indicator flag, see EX17)
3.2. Programme Head picks a suitable advisor
3.2.1. Academic case: an academic advisor specialised in that subject, or a general academic advisor of the student's faculty
3.2.2. Wellbeing case: a wellbeing advisor
3.2.3. If the student had an earlier case with an advisor of that type, that advisor is preferred (quality-of-life add-on, optional: familiar advisor-student pairs first)
3.3. System sets the case's advisor and moves the case to stage = assigned
4. System notifies both sides
4.1. Student receives the advisor's contact information by email and in-app notification
4.2. Advisor receives a notification of the new case
5. Advisor reviews the case
5.1. Opens the case: reason, category, subject
5.2. Opens the student's profile (email, full name, username, faculty, student code, academic status: always visible, not logged) and the student's data: only consented data attributes are shown, with their source and missing-data notices, and every value shown is logged
5.3. If more data is needed, the advisor sends a consent request (see EX7)
6. Advisor and student meet
6.1. They agree on when and how to meet (online, offline), e.g. in the case thread (see EX18); the app has no scheduling system (extra scope, ES7)
6.2. Advisor moves the case to stage = contacted
6.3. Advisor and student can write in the case's message thread (e.g. next steps or a meeting suggestion, and the student's reply); each message notifies the other side
7. Advisor records case notes (discussion, agreed actions) and finalizes them
   Case notes are internal staff records and are not the channel for student-facing communication; case messages are stored separately and cannot be edited or deleted
8. If the case needs someone else
8.1. Advisor refers it to another advisor of the same or the other type (see EX4)
8.2. Wellbeing Advisor refers money matters to the Welfare Officer (see WF2b)
9. Advisor follows up (stage = followUp) and closes the case (stage = closed)
10. Every stage change is recorded in the case's stage history
11. After closing, the student may rate the case once (see EX19)

WF2b: Welfare Officer handles a financial referral (continuation of WF2 step 8.2)
1. Welfare Officer sees the referral in the incoming queue
2. Welfare Officer triages it
2.1. Opens the referral and the advisor's notes
2.2. Sets the priority
2.3. Accepts it (the wellbeing advisor keeps the case and the stage stays referred), or returns it to the advisor with a reason (the case goes back to the stage it had before the referral)
3. Welfare Officer works with the student (loan arrangement, financial aid, banking documents)
3.1. Logs each intervention (type, date, notes)
3.2. Records any support grant issued
3.3. Records the outcome
4. If an outside service is needed (e.g. a money-lending service, a bank)
4.1. Welfare Officer records the external referral with an expected follow-up date
4.2. System flags it as overdue if the date passes without an outcome
4.3. Welfare Officer logs the follow-up outcome
5. If the case goes beyond the Welfare Officer's authority, it is escalated (see EX5)
6. Welfare Officer closes the intervention; the case goes back to the advisor for follow-up and closure

WF3: Steward sets up consent
1. Steward signs in
2. Steward defines the shareable data
2.1. Creates the data attributes (name, description shown to students and staff, data type numeric/categorical/boolean)
2.2. Archives data attributes that are no longer used (one-way; existing values and consents are kept)
3. Steward defines consent purposes
3.1. Creates a purpose (e.g. Academic advising, Wellbeing support, Financial support); it starts inactive
3.2. Attaches the data attributes the purpose covers (an attribute can belong to several purposes)
3.3. Activates the purpose
4. Steward configures access policies
4.1. Links a role to a purpose (the policy starts as a draft; the student's consent must be granted)
4.2. Activates the policy
4.3. Tests the policy against a sample case
5. Admin links each support category to the purpose that governs it (see EX11), so students only see the matching attributes when they request support
6. Later changes: a purpose is retired (never deleted) when no longer used; policies are revoked rather than edited

WF4: Programme Head lists, reports and exports
1. Programme Head signs in and opens the reports page
2. Chooses a time range
3. Filters by advisor, support type, category, subject or stage
4. Views the result
4.1. List of cases/consultations in the range
4.2. Caseload volume per advisor
4.3. Average time to close a case per advisor
5. Exports the list/report (Excel/CSV/PDF)
6. Views the anonymised welfare statistics and cohort data (see EX20)

WF5: Admin imports student data
1. Admin signs in and opens "Import student data"
2. Admin uploads an .xlsx/.csv file (Google Sheet import is extra scope, see ES6) and previews its header and first rows
3. Admin maps the file columns (student identifier: email, username or student code; data attribute; value; term; valid-from date)
4. System validates the whole file (it can also be validated alone, without saving)
4.1. If any row is invalid, nothing is imported and the system lists the invalid rows (all-or-nothing)
4.2. Rows of an archived data attribute are not imported; they are listed separately and the other rows still go in
4.3. Otherwise the system writes each value straight into STUDENTDATA as a new row (dataSourceId stays null), encrypted with the student's key for that attribute (created on the first value), with the file name and import date kept as its source note (provenanceNote)
5. Every enrolled student without a value for an imported attribute and term gets a missing row (missing-data notice)
6. After the import the system compares every enrolled student's latest values with the active early-support indicators and raises or clears flags (see EX17)
7. Admin views the import result and the import history
8. Note: scheduled automatic ingestion (data sources, schedules, jobs) is kept in the ERD but is extra scope (ES1, see AdviseCare_Extra_Scope_List.txt)

==========
EXTRA WORKFLOWS
==========

EX1: Account linking and first sign-in
1. User opens the account-linking email
2. User clicks the one-time link
2.1. If the link has expired, the user is told to ask the Admin to resend it
3. User signs in with the personal Google account
3.1. System checks the Google email matches the account email
3.2. System checks no other account is already linked to this Google account
3.3. System stores the Google id, sets linkStatus = linked, clears the token and signs the user in
4. Account setup step: the system offers to set a password right away, with a Skip button and the note "You can set a password in Settings"
5. User sets the preferred language
6. User lands on the home page of their role
7. Later sign-ins: "Sign in with Google" or email/username + password ("Sign in with Google" refuses any Google account that is not linked to an account)

EX2: Sign in, forgot password and sessions
1. User signs in with Google or with password
2. System checks the account status (deactivated or banned accounts are refused)
3. System opens a session and records the device; a session ends on its own 1 month after sign-in
4. Forgot password
4.1. User enters the email (only linked accounts get a reset link, valid for 1 hour; the reply is the same either way)
4.2. System emails a one-time reset link
4.3. User sets a new password; every session of the account is logged out
5. User sets or changes the password in Settings (the old password is asked only if one already exists); the other sessions are logged out
6. User views active sessions and logs out of other sessions

EX3: Advisor reaches out based on student data
1. Advisor views a student's data outside a case (only data attributes consented under a purpose the advisor's role has a policy for: "if you consent, we serve"; attributes not shared show as "exists, not shared"; every value shown is logged)
2. Advisor notices a student who needs help (merits, attendance, grades...)
3. Advisor opens a case for that student with a reason and category
4. System notifies the student that the advisor wants to meet, with the advisor's contact information
5. Continues as WF2 from step 5

EX4: Referral between advisors
1. Advisor opens the case and chooses "Refer"
2. Advisor picks the receiver (advisor of the same or the other type) and writes the reason and priority
3. Receiver gets a notification
4. Receiver accepts (becomes the handling advisor) or returns the referral with a reason (the case goes back to the stage it had before the referral)
5. Case stage history records the hand-over

EX5: Escalation to the Programme Head
1. Welfare Officer marks the case for escalation and writes the reason
2. Programme Head gets a notification
3. Programme Head records a response/decision
4. Welfare Officer sees the response and continues the case

EX6: Case advisor change
1. The student of a case, or its current advisor, requests that the case move to another advisor, proposing the advisor and a reason (CASECHANGEREQUESTS)
2. Programme Head reviews the request
3. Programme Head approves or rejects it
3.1. Approved: the case's advisor becomes the proposed advisor
3.2. Rejected: the Programme Head's reason is recorded (decisionNotes) and the case keeps its advisor
4. Both advisors and the student are notified
5. Programme Head can also reassign directly without a request

EX7: Advisor asks for more data (consent request)
1. Advisor picks the student, the purpose and the data attribute needed
2. Advisor states the purpose
3. Student gets a notification and grants or denies
3.1. Granted: a consent record is created under the request's purpose and the advisor can now see the value
3.2. Denied: the advisor sees the attribute as "exists, not shared"
4. Advisor can withdraw a request that is still pending

EX8: Student manages consent and erasure
1. Student opens the consent page and sees each purpose and its attributes
2. Student grants or withdraws consent per purpose, or withdraws single attributes of a purpose
3. Every change is recorded in consent history
4. On withdrawal
4.1. Access is blocked immediately
4.2. An erasure request is queued (when the attribute is no longer shared under any purpose and values are stored)
4.3. Steward verifies the withdrawal and executes the erasure: the attribute key is destroyed and every value it protected is cleared, in one step
4.4. The values become unreadable; the audit trail stays (the rows stay, marked as erased)
4.5. Student is notified

EX9: Access log review
1. Every time staff open student data, the system checks role + purpose + consent and logs the access
2. Student views own access log and may flag an entry
3. Steward searches/filters the access log, reviews flagged entries and exports processing records

EX10: Emergency access
1. Staff requests access beyond consent with a justification
2. A Steward approves with a time limit, or rejects with a reason (Stewards share one pool of requests; the first to act decides)
3. While approved, the requester can read every attribute of that student; access ends automatically when the time limit passes; every access is logged (as an emergency access, without a purpose)

EX11: Master data setup
1. Admin manages academic terms (create, edit, set status; only one term can be current)
2. Admin manages faculties and subjects (subjects belong to a faculty)
3. Admin links academic advisors to the subjects they specialise in
4. Admin manages support categories (name, academic/wellbeing, governing consent purpose)

EX12: Account management
1. Admin opens an account from the dashboard
2. Admin edits the account details (email, full name, username, faculty); changing the email unlinks the Google account and the linking email has to be sent again
3. Admin adjusts roles (the last System Administrator role cannot be removed); giving the Student role to an account without a student profile also asks for studentCode and academicStatus
3.1. Admin edits a Student account's student profile (studentCode, academicStatus), e.g. enrolled -> onLeave when the student takes a leave of absence
4. Admin deactivates/activates or bans/unbans the account (not their own account)
5. Deactivating or banning ends all active sessions of the account

EX13: Point-in-time reconstruction ("way back machine")
1. Advisor opens a student and clicks "View as of date"
2. Advisor picks the date and the time axis
2.1. System time: what AdviseCare knew on that date (the latest value recorded by then), e.g. to see what an advisor saw when acting
2.2. Valid time: what was really true on that date by today's knowledge (corrections recorded later included)
3. System rebuilds the record (only computed on request); the same consent rules apply
4. Advisor can compare two dates on the same time axis; every value shown is logged with its exact row

EX14: Student exports own record
1. Student opens account settings and chooses "Export my data"
2. System builds a JSON file with the student's record and access log
3. Student downloads it; the export is logged

EX15: Correction request
A student asks for a wrong value in their own student data (e.g. an attendance rate) to be corrected; directory data (name, student code, academic status) is edited by the admin instead.
It works like a case for one data attribute, but never opens a case (QC-214)
1. Student picks the value believed to be wrong (one data attribute for one term), the consent purpose to send it under (only purposes that cover the attribute), the correct value and a reason
2. Submitting also gives consent on that one attribute under that purpose (an existing consent is kept), so the reviewers can read the value
3. Every advisor whose role has an active access policy for the purpose sees the request in their correction request list (a shared pool, shown separately from cases)
4. The first advisor to decide reviews it against its source (e.g. the lecturer's attendance sheet) and is stored as the reviewer
5. Approved: the corrected value is saved as a new version with the same valid-from date, and the wrong value stays in the history (system time still shows the old value, valid time shows the corrected one); Rejected: the advisor writes the reason
6. Student is notified; while pending, the student can track or withdraw the request

EX16: Notifications, language and settings
1. User views notifications, marks them read, clicks through to the item and clears old ones
2. User sets notification preferences (email/in-app)
3. User switches language (Vietnamese/English); the choice is remembered
4. User views own activity history and edits account settings (username, avatar)

EX17: Early-support indicators (owner: Member A)
1. Steward defines an indicator: a rule on one data attribute (comparison and threshold, e.g. Attendance rate < 75), its severity (low/moderate/high/critical), the case priority (low/medium/high/urgent) and the support category a case would get; it starts as a draft and is activated, edited or archived later
2. After every student data import (and when a rule is activated or changed) the system compares each enrolled student's latest value per term with every active rule
2.1. A hit raises a flag (one open flag per student, rule and term); a later value that no longer hits the rule clears an open flag
2.2. The check runs inside the server only: it is not an access by a person and writes no access log
3. Staff see a flagged student's directory data, the rule (name, description), severity, priority and term, but never the value; the value stays behind consent
4. Programme Head works through the flag queue (severity, then priority, then oldest)
4.1. Opens a case from a flag for an advisor of the rule's support type (the case gets the rule's priority and category; the flag is linked to the case), or
4.2. Dismisses the flag with a reason
5. An advisor can ask to take a flagged student on; the Programme Head approves it (a case is opened for that advisor) or turns it down (the flag goes back to open)
6. Cases are never opened automatically; the student is notified as in EX3 and the case continues as WF2 from step 5

EX18: Case thread (owner: Member B)
1. The student of a case and its current advisor write messages in the case's thread; each message notifies the other side
2. A student can write once an advisor is assigned; nothing can be added while the case is closed; messages cannot be edited or deleted
3. The Programme Head and referral staff can read the thread
4. Still to be decided with Member B (tracked in the Q&A history): real-time or not, attachments, read receipts, who else may write and when, message length and rate limits

EX19: Case feedback and ratings (owner: Member D)
1. After a case is closed, its student may rate it once: 1-5 stars and an optional comment
2. The rating stays tied to the advisor who handled the case (CASEFEEDBACKS.advisorId), even if the case is reopened or reassigned later
3. Still to be decided with Member D (tracked in the Q&A history): who may read the feedback (the advisor, the Programme Head), whether it is anonymous to the advisor, and whether ratings feed the advisor suggestion algorithm (ES4)

EX20: Anonymised welfare statistics and cohort data
1. Welfare statistics (Student Welfare Officer, Programme Head)
1.1. Chooses a date range, and optionally a faculty, a support type and a split per faculty
1.2. Views per support category: cases opened, referred cases, interventions, support grants, external referrals and escalations in the range, and the number of different students behind them
1.3. Every cell counted from fewer than 5 different students is hidden; no student-level data is shown
1.4. Exports the statistics (Excel/CSV/PDF); the export is logged
2. Cohort data (Programme Head)
2.1. Chooses one data attribute and one term, and optionally a faculty or a split per faculty
2.2. Views the average, minimum and maximum (numeric attribute) or the number of students per value (categorical/boolean attribute)
2.3. Only the latest value of students who shared it under the statistics consent purpose (set up by the Steward) counts; emergency access never counts
2.4. Every value read is written to the access log; every cell or value with fewer than 10 students is hidden
2.5. Exports the cohort data (Excel/CSV/PDF); the export is logged

==========
EXTRA SCOPE (backup plans, not in the current version; details in AdviseCare_Extra_Scope_List.txt)
==========

ES1: Scheduled data ingestion / live integration with FAP, FLM, LMS (data sources, schedules, jobs; one upcoming job per schedule, warn/skip/retry on failure)
ES2: Stored report history (reports and statistics are generated and downloaded on the fly for now)
ES3: Backup and restore with integrity check
ES4: Advisor suggestion algorithm that ranks advisors for the Programme Head (support category, subjects, familiar pair, caseload, ratings; the Programme Head still decides)
ES5: Evaluating the effectiveness of advising over a period
ES6: Importing accounts and student data from a Google Sheet (Excel/CSV import only for now)
ES7: Meeting scheduling inside the app (advisor time slots, students book, advisors swap)
ES8: AI assistance in the case thread (e.g. suggested replies or summaries); not agreed by the team yet
ES9: Accounts without a Google account on file, created with a one-time activation code
ES10: Account import that also updates existing accounts (matched by studentCode; a new studentCode creates the account as today)
ES11: Each student's programme (only needed once there is more than one programme / Programme Head)
ES12: Anonymised statistics for the other roles (cases, consents, imports, accounts; small groups hidden)
ES13: AI advisor as a backup when there are not enough advisors (the Programme Head always decides)
ES14: Advisor profiles (expertise, languages, working style) for the suggestion algorithm
ES15: Admin configuration panel (system settings changed without a new deployment)
