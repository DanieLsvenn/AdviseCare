ADVISECARE API WORKFLOWS (current version)

API version of AdviseCare_Workflow_List.txt. The step numbers and names are the same as there, and each step shows the endpoint(s) it calls plus test input.
For the meaning and rules of each step, read AdviseCare_Workflow_List.txt. This file only covers how to test the steps through the API.

==========
HOW TO READ THIS FILE
==========

Endpoint tags
- [EXISTS] - the endpoint is in the backend now; endpoints not used by a numbered step are listed in the EXTRA ENDPOINTS section at the end
- [PLANNED] - not built yet; the route and body are a proposal following the same conventions, to be confirmed by the member who owns it (see AdviseCare_Backend_Task_Division.txt)
- [NO API] - the step happens outside the backend (web app page, email inbox, Google)

Unhappy cases (QC-202)
- Every step with an endpoint also lists its unhappy cases and their results, so a tester can check each refusal:
  "Negative:" lines are hand-written cases with their exact input; "Unhappy:" lines list every error the route can answer
  (taken from the route's Swagger error list), each as: how to trigger it -> status "message"
- Every error answer has the body { "message": "..." }; a request that fails its DataAnnotations answers 400 with an "errors" object per field instead
- Swagger UI shows the same list under each route's 400/401/403/404/409 responses

Step layout
N. Step name (same as AdviseCare_Workflow_List.txt)
   METHOD /api/Route [tag]
   Auth: which token to send (Authorization: Bearer {token})
   Body / Query / Form: test input
   Expect: what a correct response looks like
   Save: values from the response used in later steps

Conventions
- Base URL: https://localhost:{port} locally, the MonsterASP URL once deployed
- JSON is camelCase; enum values are sent as strings exactly as in the database (e.g. "notLinked", "followUp"); dates are UTC ISO 8601
- {curlyName} is a placeholder for a value saved in an earlier step (ids, tokens)
- Get-all endpoints accept the optional query ?page=1&pageSize=20; search endpoints take their filters as query parameters, empty filters are ignored
- Planned routes follow the existing pattern: one controller per main table (api/[controller], plural entity name), junction tables as sub-routes of the owning controller (like /api/Accounts/roles and /api/Subjects/account-subjects), own data under /me
- createdBy/openedBy/assignedBy-type fields are never in the body; the server takes them from the JWT

Rules worth knowing when testing
- CASES.advisorId is the only advisor-student link (no ADVISORASSIGNMENTS): an advisor advises a student while holding one of their cases that is not closed
- Notifications about cases point to /cases/{caseId}, /referrals/{referralId} or /case-change-requests/{id}; opening GET /api/Cases/{id} marks the caller's notifications for that case as read, which drives unreadNotificationCount in /api/Cases/assigned
- Case notes: only the case's current advisor writes; drafts are private; students never read notes
- Case messages: a two-way thread separate from case notes; the student and the current advisor write (not on a closed case), and the student, current advisor, Programme Head and staff involved in a case referral read; messages are append-only and each one notifies the other side
- A case with a pending referral cannot change stage, be reassigned or have a change request approved until the receiver accepts or returns it
- Welfare Officer accepting a referral does not take the case: the advisor keeps it (stage stays referred) and moves it to followUp after the welfare work
- Advisor outreach (EX3) works for any active student, but only with a category of the advisor's own type
- Case change requests and direct reassignment only accept an advisor of the case's type (academic -> Academic Advisor, wellbeing -> Wellbeing Advisor); referrals may go to the other type or the Welfare Officer
