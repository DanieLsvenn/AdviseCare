ADVISECARE FUTURE LIST (features not in the current version)

Same numbering as the FUTURE section of AdviseCare_Workflow_List.txt.

==========
1. FUTURE, ALREADY IN THE ERD
(the tables or data already exist in AdviseCare_ERD_Tables.txt, but no feature is built on them in the current version)
==========

FU1: Scheduled data ingestion / live integration with FAP, FLM, LMS
- What it is: connect to a real data source (database, API) and pull indicator data automatically on a schedule, instead of the admin uploading Excel/CSV/Google Sheet files
- Already in the ERD: DATASOURCES (one data source per indicator), INGESTIONSCHEDULES, INGESTIONJOBS, and STUDENTINDICATORS.dataSourceId (null for file imports in the current version)
- Rules already decided: one upcoming job per schedule, minimum frequency daily, start time works like an alarm, on failure warn/skip/retry, every job is all-or-nothing
- Why future: the school offers no data source or API for FAP, FLM or LMS

FU2: Stored report history
- What it is: keep every generated report/export so it can be downloaded again later
- Already in the ERD: REPORTS
- Current version instead: case reports and the student JSON export are generated and downloaded on the fly, not stored

FU3: Backup and restore with integrity check
- What it is: pick a backup point, restore it, and verify nothing is missing or duplicated
- Already in the ERD: BACKUPS, RESTOREOPERATIONS
- Why future: database backups are handled by the hosting for now

FU4: Automated / AI case matching
- What it is: the system suggests or picks the advisor for a new case, replacing the Programme Head's manual matching
- Already in the ERD: no extra table needed; it would use CASES, ADVISORASSIGNMENTS, ACCOUNT_SUBJECT and SUBJECTS
- Includes: prioritising a familiar advisor-student pair (quality-of-life add-on, can also be added to manual matching earlier if time allows)

FU5: Advising effectiveness analysis
- What it is: analyse case data over a period (a month, a term) to help the school judge whether advising works
- Already in the ERD: no extra table needed; it would use CASES, CASESTAGEHISTORIES, REFERRALS and INTERVENTIONS
- Why future: the mentor stated this software matches and tracks; judging effectiveness is not its responsibility

FU6: Importing accounts from a Google Sheet
- What it is: the admin pastes a Google Sheet link instead of uploading an Excel file; the rows go through the same all-or-nothing validation as the Excel import
- Already in the ERD: no extra table needed; it creates the same ACCOUNTS and ACCOUNT_ROLE rows as the Excel import
- Why future: kept simple for now, the admin can download the sheet as an Excel file and upload that
- Ways to do it later: a sheet shared as "anyone with the link can view" read through its CSV export link (no API key), or a Google service account for private sheets

FU10: Account import that also updates existing accounts
- What it is: the same Excel import, but a Student row whose studentCode already exists updates that student (e.g. academicStatus enrolled -> onLeave, a new faculty) instead of being refused; a row with a new studentCode creates the account exactly like today
- Already in the ERD: no extra table needed; it updates ACCOUNTS and STUDENTPROFILES
- Current version instead: the import only creates accounts, and the admin edits a student's profile one by one (PUT /api/Accounts/{id}/student-profile)

FU12: Anonymised welfare statistics
- What it is: a summary page for the Student Welfare Officer showing how many support cases were opened in each support category over one academic term or a chosen date range, e.g. "Fall 2026 - Money: 23 cases from 19 students; Accommodation: 11 cases from 10 students", with a CSV export. It shows counts only: no names, no student codes, no case text
- Why "anonymised": counts alone can still point at a person. If a category had only 1 or 2 students in a term, anyone who knows who asked for help could tell what it was about, so every category with fewer than 5 different students is hidden from the result (small-group suppression); an overall total is also left out, so a hidden category cannot be worked out by subtracting
- Already in the ERD: no extra table needed; it counts CASES (openedAt, studentId, supportCategoryId) grouped by SUPPORTCATEGORIES, using ACADEMICTERMS for the term's dates; REPORTS.reportType already has "welfareStatistics" for when generated reports are stored (FU2)
- Questions to settle before building it: count every support category or only the wellbeing/financial ones the Welfare Officer works with; who may see it (Welfare Officer only, or also the Programme Head); count by the date a case was opened or by the cases that were active in the period; the suppression threshold (5 students); whether interventions and support grants should be counted too
- Why future: it reads only data produced by the case workflow (Member D), it is not one of the 5 core workflows, and it was left "pending review" in the requirements
- Earlier prototype: Member C built a version of it (commit 274023e on the C branch; described in Documentation/C), removed from the current code

FU13: Anonymised cohort indicators
- What it is: a summary of student indicators for a group of students (a cohort): one term, one faculty, or both. A numeric indicator shows its average and the number of students behind it (e.g. "Fall 2026, faculty SE: average attendance rate 82%, 134 students"); a categorical or boolean indicator shows how many students fall in each value (e.g. "Accommodation status: dormitory 61, rented 52, family 21"). Staff can export the same summary as CSV. No single student's value or identity is ever shown
- Why it is harder than it looks: an average is still built from each student's personal, encrypted value, so the "if you consent, we serve" rule still applies to every value that goes into it:
  + the student must have consented to that attribute under a purpose meant for statistics (e.g. a "Cohort Analytics" consent purpose created by the Steward), and the reader's role must have an active access policy for that purpose; values shared only for advising do not count
  + each value is decrypted only after the access guard allows it, and every value read is written to ACCESSLOGS (one statistic can mean hundreds of log rows)
  + only the latest value per student, indicator and term is used; missing, erased and archived-indicator values are left out
  + every result cell with fewer than 10 different students is hidden, so nobody can recover one student's value from a small group
  + emergency access never counts here, since it is meant for one student in an urgent situation, not for statistics
- Already in the ERD: no extra table needed; it reads STUDENTINDICATORS, INDICATORS, ACADEMICTERMS, ACCOUNTS.facultyId and the consent tables (CONSENTPURPOSES, CONSENTS, ACCESSPOLICIES, ACCESSLOGS); it only needs a consent purpose for statistics set up by the Steward
- Questions to settle before building it: which roles may use it; how the system recognises the statistics purpose (a configuration value or a flag on CONSENTPURPOSES, not the purpose's name); the threshold (10 students); whether a statistic should write one access log row per value or one summary row
- Why future: it depends on the indicator import, consent and encryption all being finished (the key system choice is still open), it is not one of the 5 core workflows, and it was left "pending review" in the requirements
- Earlier prototype: Member C built a version of it (commit 2ab7f75 on the C branch; described in Documentation/C), removed from the current code

2. FUTURE, NOT IN THE ERD
(would need new tables or changes to existing ones)
==========

FU7: In-app meeting scheduling
- What it is: advisors publish available time slots, students book them, advisors can swap meetings with each other
- Missing in the ERD: tables for advisor availability and meetings
- Current version instead: advisor and student decide by themselves when and how to meet; the system only sends the advisor's contact information and the advisor records case notes

FU8: In-app chat between advisor and student
- What it is: messaging inside the platform instead of external apps
- Missing in the ERD: tables for conversations and messages
- Note: possible stretch goal if the scope turns out too small

FU9: Accounts without a Google account on file (activation code)
- What it is: the admin creates an account without a Google-linked email. The system shows a one-time activation code, valid for a short time, which the admin gives to the student in person. The student enters the code, sets their own password straight away, and links a Google account later in Settings
- Missing in the ERD: no new table, but ACCOUNTS.email must allow null (the unique index has to ignore nulls), and the code can reuse resetToken and resetTokenExpiresAt
- Why future: the current version expects every student to have an email and a Google account, so this is only a fallback for students who cannot or will not share one
- Open points: how notifications and "forgot password" work for an account with no email; the code is shown only on the admin screen, never sent by email

FU11: Each student's programme
- What it is: record which programme each student belongs to, so cases and statistics can be split per programme and routed to that programme's head
- Missing in the ERD: STUDENTPROFILES.programmeId (FK to PROGRAMMES)
- Why future: there is only one programme / Programme Head for now; the faculty on ACCOUNTS is enough to group students
